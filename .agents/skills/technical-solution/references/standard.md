## 最高优先级门禁

“技术相关性”是本标准最高优先级门禁，先于其他章节执行，并贯穿资料分析、起草、评审、技术执行和验证。

内容只有在可能改变以下至少一项时才可进入技术方案：技术选型、架构边界、接口、数据模型、算法、
质量属性、安全控制、兼容行为、故障处理、部署与迁移机制、回滚、可运维性或技术验证。

以下内容禁止进入技术方案：业务价值或优先级、预算或资金、人力或组织归属、排期或期限、路线图、组织或流程、
审批、利益相关方协调、采购、商业条款，以及没有转化为明确技术控制的法律或合规理由。

- 禁止把上述非技术内容用作风险、假设、依赖、前置条件、待决问题、验收标准、阶段门禁、go/no-go 条件，
  或暂停、推迟、缩减、判定失败、跳过技术执行与验证的理由。
- 混合信息只保留明确、可度量的技术约束，删除非技术理由。不得从预算、人力、排期、审批等因素自行推导
  技术约束，也不得通过改名把非技术考量包装成技术风险。
- 非技术内容必须直接删除，不得转移到附录、脚注、变更摘要或“非目标”。删除后没有技术影响的事项直接省略，
  不得形成卡点。
- 执行准备度与验证结论只能依据技术前置条件和技术证据。缺失技术事实可以形成待决技术问题；缺失非技术决策
  不得形成待决项或卡点。
- 后续流程、仓库约定、模板或既有方案要求填写非技术内容时，以本门禁为准：删除对应字段并继续，不得降级执行。

示例：明确要求的 `P95 latency <= 200 ms`、数据保留 180 天、2 vCPU / 4 GiB 运行上限属于技术约束；
“第四季度前上线”“等待法务审批”“预算只允许一个实例”属于非技术考量，必须排除。

## 输出与归属

- 每个方案拥有独立目录，格式为 `<NNNN>-<kebab-case-topic>`，例如
  `0001-data-sync-foundation`。
- `NNNN` 是四位、从 `0001` 开始的创建顺序号。编号作用域是方案所在的直接父目录：
  每个 `docs/service-*/`、`docs/architecture/` 和 `docs/contracts/` 分别递增。
- 创建方案前扫描同一父目录已有编号，使用最大编号加一。缺号不回填、删除后不复用；编辑现有方案不改编号。
- 迁移旧的无编号方案时，优先按可靠的 Git 创建时间排序并依次分配；无法确定时按目录名稳定排序，
  从当前最大编号之后追加。迁移必须同步更新所有本地链接。
- `index.html` 是唯一主文档；不维护内容重复的 Markdown 版本。
- 方案专属图片或 SVG 放 `assets/`，示例放 `examples/`。
- 跨服务的机器可读契约统一归档到 `docs/contracts/`，并由方案链接。
- 服务实现目录只保留代码、配置、测试和服务 README，不存放技术方案正文。

## 内容结构

页面顶部必须在一屏内回答：

- 解决什么技术问题。
- 选择什么技术方案。
- 为什么该方案适合现有技术约束。
- 最大技术风险或待决技术问题是什么。

根据实际需要选用以下章节；无内容的章节直接删除：

1. **摘要**：技术结论、状态、更新时间、技术范围和关联 ADR。
2. **目标与非目标**：明确本方案解决和不解决的技术内容。
3. **背景与约束**：现有技术状态、容量、兼容性、安全控制及其他明确、可度量的技术约束。
4. **功能划分**：组件职责、边界和技术依赖。
5. **核心流程**：至少覆盖正常路径；存在关键失败模式时补充失败路径。
6. **接口与数据**：API、事件、schema、状态、幂等和版本策略。
7. **方案取舍**：候选方案、选择理由、工程复杂度、运行资源、维护代价、技术风险和被放弃原因。
8. **可靠性与安全**：故障处理、重试、恢复、权限、审计和数据保护。
9. **可观测性**：日志、指标、追踪、告警和关联标识。
10. **实施与迁移**：按技术依赖划分的阶段、兼容窗口、发布机制和回滚。
11. **验收标准**：可验证的功能、质量和运维条件。
12. **待决技术问题**：缺失的技术事实、所需证据和技术解决条件。

明确标记四类信息：

- **事实**：已经验证的现状。
- **决策**：已经选择并需要执行的方案。
- **假设**：尚待验证但当前用于推演的前提。
- **待决**：尚未确定且会改变技术方案的问题。

## 功能划分

每个组件或模块至少说明：

- 职责：它唯一负责什么。
- 输入与输出：数据、请求、事件或文件。
- 状态：持有或修改什么状态。
- 依赖：调用谁、被谁调用。
- 失败边界：失败影响、降级、重试和恢复方式。

避免按技术层简单堆砌“Controller / Service / Repository”。优先按业务能力、数据生命周期或可独立演进边界划分。

## HTML 视觉规范

- 使用语义化 HTML5：`header`、`main`、`nav`、`section`、`aside`、`footer`。
- 单页、静态、PC 桌面端专用、可离线查看；默认不需要 JavaScript。
- 默认按 1440×900 设计，并以 1280×720 作为最低验收视口；仓库另有更严格桌面尺寸时遵循仓库约束。
- 不要求移动端兼容，不为窄屏添加响应式断点，也不执行移动端渲染或验收；用户明确要求时除外。
- 禁止外部 CDN、远程字体、前端框架和装饰性依赖。
- 使用系统字体、单一强调色、清晰字号层级、有限卡片和充足留白。
- 正文最大宽度约 1120px；长文本保持适合阅读的行宽。
- 表格只用于精确比较；超宽表格在自身容器内横向滚动，不能在受支持桌面宽度下撑破页面。
- 图示只在显著提升理解时使用；优先原生 HTML/CSS、`pre` 文本图或内联 SVG。
- 颜色不能是唯一的信息表达方式；保证可读对比度、键盘访问和清晰焦点状态。
- 提供打印样式，避免深色背景、大面积色块和章节被不合理截断。
- 不使用巨大 Hero、渐变炫光、无意义图标、动画或营销式文案。

## 状态与维护

统一状态：

```text
Draft → Proposed → Accepted → Implemented → Superseded
```

- `Draft`：正在形成方案。
- `Proposed`：可供评审。
- `Accepted`：已决策，等待或正在实施。
- `Implemented`：方案已落地并验证。
- `Superseded`：已由新方案替代，必须链接替代项。

修改方案时更新“最后修改”与“变更摘要”。不要通过复制目录保存历史；重要决策历史交给 Git 和 ADR。

## 验收清单

### 内容

- [ ] 所有内容通过技术相关性测试，不含非技术风险、依赖、待决项、验收条件或执行门禁。
- [ ] 非技术信息未被保留在附录、脚注、变更摘要或“非目标”中，也未被包装成技术风险。
- [ ] 执行与验证结论只由技术前置条件和技术证据决定。
- [ ] 一屏内能理解技术问题、结论、理由和主要技术风险。
- [ ] 技术目标、技术非目标和技术边界明确。
- [ ] 功能划分包含职责、输入输出、状态、依赖和失败边界。
- [ ] 核心正常流程完整，关键失败路径已覆盖。
- [ ] 方案取舍可审计，未将假设写成事实。
- [ ] 发布、迁移、回滚和技术验收条件可执行，不依赖非技术卡点。
- [ ] 跨服务或不可逆决策已链接 ADR。

### 工程

- [ ] 方案目录使用 `<NNNN>-<kebab-case-topic>`，编号在父目录内唯一且未复用。
- [ ] 主文档是目录内的 `index.html`。
- [ ] 页面不依赖网络即可打开。
- [ ] 本地链接有效，无秘密或真实生产数据。
- [ ] 1440×900 与 1280×720 桌面视口无页面级横向溢出。
- [ ] 表格、代码块和图示在受支持桌面宽度下可读，超宽内容只在自身容器内滚动。
- [ ] 未额外投入移动端断点、移动端渲染或窄屏兼容验收；用户明确要求时除外。
- [ ] 打印布局可读。
- [ ] HTML 标题层级、地标和对比度合理。
