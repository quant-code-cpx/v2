# 0002：同步数据归属与跨服务访问

- 状态：Proposed
- 日期：2026-07-25
- 决策者：项目维护者

## 背景

`service-data-sync` 负责从外部数据源获取、标准化和修订金融数据，`service-api` 负责对外业务查询。两者需要独立构建、部署、迁移和恢复。若 API 服务直接读取同步服务数据库，会共享表结构、迁移节奏和数据库权限，破坏服务边界；若所有数据都通过同步服务实时查询，API 可用性和延迟又会受同步服务影响。

本 ADR 只确定未来数据所有权和访问方向。`0001-data-sync-foundation` 不实现接口、不创建 OpenAPI，也不设计或创建业务表。

## 候选方案

1. 两个服务共享数据库或 schema，API 使用只读账号直接查询同步表。
   - 优点：实现快、少一次网络调用、适合复杂 SQL。
   - 缺点：数据库 schema 成为隐式跨服务契约；迁移、权限、容量和故障相互耦合。
2. 同步服务独占存储，通过版本化内部 HTTP API 提供当前数据和增量变更。
   - 优点：数据所有权清晰；契约可测试、可演进；API 服务无需了解同步表结构。
   - 缺点：增加网络调用、分页和服务可用性治理。
3. 同步服务发布事件，API 服务持续构建自己的完整读模型。
   - 优点：运行时解耦、读性能高、可支持多个消费者。
   - 缺点：初期需要事件平台、回放、顺序和 schema 治理，运维成本最高。

## 决策

未来跨服务访问采用方案 2，并为方案 3 保留平滑演进路径。

- 同步服务未来独占 PostgreSQL 数据库、数据库账号、迁移和备份；生产环境优先独立数据库实例。本地开发可共享 PostgreSQL 容器，但必须使用独立 database 和 role。
- 同步服务未来独占原始数据对象存储 bucket。API 服务不获得同步数据库或 bucket 凭据。
- API 服务未来通过版本化内部 HTTP 接口读取数据、提交手动同步、读取任务状态和修改允许运行时变更的同步配置。
- 查询、分页、增量、删除语义和投影方式由后续独立编号方案确定，不在本 ADR 中提前固化。
- API 服务可在自身边界内缓存或保存读模型，但不得把同步服务数据库 schema 当成契约。
- 初期不引入跨服务事件平台。出现多个数据消费者、分钟级推送需求或 HTTP 拉取成为瓶颈时，再通过新 ADR 引入事件发布。

## 后果

- 数据模型落地后可独立迁移，API 只受显式接口契约和数据语义版本约束。
- 接口落地后，API 服务需要处理超时、重试、缓存和同步服务暂时不可用。
- 同步服务查询接口将成为内部生产接口，需要容量限制、鉴权、SLO 和兼容策略。
- 查询规模、分页和导出能力留给后续接口方案决定。
- 禁止为短期性能绕过接口授予 API 数据库读取权限；若接口确实成为瓶颈，优先建立 API 自有投影。
