Docker 开发与生产环境

公共 Compose 保存唯一拓扑，开发和生产 override 只表达环境差异。开发获得热更新和回环端口； 生产只使用不可变镜像、隔离基础设施网络，并从受保护环境文件或 secret 注入凭据。

摘要

事实

单文件混合多种语义

原 Compose 同时包含本地端口、测试容器和生产镜像阶段，无法一眼判断发布面与 secret 边界。

决策

公共拓扑 + 双 override

compose.yaml 保存公共关系，开发和生产文件仅覆盖 build、端口、挂载、镜像及安全策略。

主要风险

生产仍是单节点基线

TLS、反向代理、HA、托管存储和 secret manager 尚未选型；本方案不把单机 Compose 描述成最终平台。

目标与边界

目标

  • 三个服务可独立选择 profile、构建和运行。
  • 开发支持 Web/API 热更新及本机依赖调试。
  • 生产隐藏状态服务端口并强制发布镜像引用。
  • 真实凭据只进入不提交的配置源。

非目标

  • 不决定云厂商、Kubernetes 或托管数据库。
  • 不新增未冻结的跨服务 API 或数据同步任务。
  • 不在 Compose 内实现 TLS、证书签发或镜像发布。

约束

  • API migration 必须与应用启动分离。
  • 同步 worker 需要受控外部网络出口。
  • VITE_* 是构建时公开值，不是运行时 secret。
  • 日常停止不得删除 named volume。

功能划分

Common

compose.yaml

职责：服务依赖、健康检查、容器内连接、网络和持久卷。

输入 / 输出：环境变量输入；输出稳定公共拓扑。

状态：仅声明 named volume，不持有凭据。

失败边界：依赖不健康时阻止下游进程启动。

Development

compose.dev.yaml

职责：本地 build target、源码挂载、热更新、测试服务和回环端口。

输入 / 输出：读取本地 .env；输出可调试容器。

状态：使用开发项目名隔离 volume。

失败边界：只影响开发项目，不触及生产 volume 或网络。

Production

compose.prod.yaml

职责：不可变镜像、公开业务端口、内部网络和业务容器最小权限。

输入 / 输出：读取受保护配置；输出单节点生产拓扑。

状态：生产项目名下的独立 volume。

失败边界：migration 失败时 API 不启动；状态服务不暴露宿主机端口。

核心流程

开发者 / 部署流程
  │
  ├─ 选择 compose.yaml + compose.dev.yaml
  │    └─ 本地 build → 依赖 healthy → migration → API / Web / worker
  │
  └─ 选择 compose.yaml + compose.prod.yaml
       └─ 校验 secret 与 digest → 拉取镜像 → 依赖 healthy → migration
                                                  └─ 成功后启动 API

浏览器 ──▶ Web / API 公共端口
API ──▶ API PostgreSQL + Redis（生产 internal network）
data-sync worker ──▶ PostgreSQL + Redis + MinIO（internal）
                 └─▶ 外部 provider（独立 egress network）
关键失败路径 生产 migration 非零退出时，service-api 的 service_completed_successfully 条件不满足。修复配置或 migration 后重跑； 不允许通过绕过 migration 条件强行启动新版本。

配置与安全

分类示例开发来源生产要求
Secret DB/Redis 密码、JWT secret、MinIO/S3 secret、管理员初始密码 Git 忽略的根 .env 受保护 env 文件或 secret manager；禁止进入镜像和仓库
非敏感运行配置 端口、issuer、TTL、日志级别、bucket、CORS origin .env，契约见 .env.example 按环境显式配置并接受发布审查
浏览器公开配置 VITE_API_BASE_URL 开发进程环境 构建 Web 发布镜像时注入；不得放 secret
发布供应链 *_IMAGE_REF 开发文件忽略 必须替换为发布 CI 生成的 immutable digest

根环境变量模板只包含保留域名、零 digest 和开发假凭据。 它用于契约审查和 CI，不构成生产默认值。

方案取舍

候选优势成本 / 风险结论
公共文件 + 双 override 公共拓扑唯一；环境差异可审查；保留服务 profile 命令必须指定两个文件；需查看 merge 后结果 采用
两份完整 Compose 单文件即可启动；阅读直接 依赖、健康检查、网络和 volume 重复漂移 不采用
单文件 + profile 切环境 文件少 profile 不适合表达 mount、build、端口和安全策略覆盖 不采用

实施与验收

  1. 配置：从 .env.example 创建不提交的 .env，替换本地 secret。
  2. 开发：合并公共与开发文件，按 profile 构建；验证健康检查、热更新和集成测试。
  3. 发布：分别构建四个发布镜像，推送后记录 digest；先执行 production config 审查。
  4. 启动：基础设施健康后执行 migration；migration 成功才启动长期业务容器。

验收标准

  • 开发与生产 Compose 均通过 config --quiet。
  • 三个 runtime 镜像为非 root，健康检查可用。
  • 生产状态服务无宿主机端口，内部网络隔离。
  • 仓库不跟踪 .env 或真实 secret。

回滚

保留 volume，停止当前项目，恢复上一组 Compose 与镜像 digest。schema 回滚按独立 migration 流程执行；禁止用 down -v 作为部署回滚。

  • 托管存储与 HA — 容量/SLO 明确后决定。
  • secret manager 与镜像签名 — 发布流水线方案决定。
