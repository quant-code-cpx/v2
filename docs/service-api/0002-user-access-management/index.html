用户访问管理与登录安全

为“Apex数据智能分析平台”在现有 User/Auth 基线上加入自定义账号登录、全局默认鉴权、常驻图形验证码、三级固定角色和完整用户管理。 采用 PostgreSQL 权威状态、Redis 短期安全状态、目标级授权与软删除；最大风险是新枚举与旧客户端不兼容， 必须在受控未发布窗口协同升级。

摘要

事实

已有可复用 User/Auth 垂直切片

现有 API 已有 Argon2id、JWT、Refresh Session、Redis 限流、Prisma 用户/凭证/会话/审计表、 securityVersion 与独立 bootstrap job 自动超级管理员引导。

决策

默认拒绝 + 固定三级角色

全局 Guard 保护所有业务路由；登录、常驻图形验证码、刷新与幂等退出清理使用显式安全例外。 ADMIN 只管理普通用户，SUPER_ADMIN 管理管理员。

主要风险

角色枚举会破坏旧客户端穷举

只有确认无外部消费者时才沿用 /api/v1 协同升级；若发现独立消费者，必须改用 /api/v2，不能让旧 Prisma Client 读取新枚举值。

需求解释假设 原始表述中“未登录不允许访问登录接口和验证码接口”与登录流程矛盾。本方案按“除登录、验证码、 Refresh Cookie 刷新与同源幂等退出清理外，未登录不得访问业务接口”设计。/health、 /ready 是受网络边界保护的运维例外。

目标、非目标与能力卡

目标

  • 账号密码登录，无注册入口；登录页始终展示并校验图形验证码。
  • 新增路由默认认证，前后端按统一权限控制路由、菜单和操作。
  • 超级管理员创建管理员，管理员只能管理普通用户。
  • 用户列表、详情、创建、修改、软删除、重置密码可审计、可并发控制。
  • 所有安全变更通过 securityVersion 立即使旧会话失效。

非目标

  • 公共注册、邀请注册、自助找回密码、短信或邮件通道。
  • OAuth、MFA、SSO、多租户和自定义角色/权限编辑器。
  • 硬删除用户、账号复用、审计匿名化和用户恢复 API。
  • 行情或 data-sync 接口；本能力无跨服务依赖。

约束与待定预算

  • 创建用户时校验账号：trim 后转小写，5–32 位，字符集为 [a-z0-9._-]。
  • 登录只校验账号非空且不超过 32 位，格式错误与未知账号统一按凭据错误处理。
  • 账号创建后不可编辑；软删除后仍保留占用，数据库以 normalizedAccount 保证唯一。
  • 单租户；Web/API 默认同站部署。
  • 用户 JSON body 目标上限 16 KiB，列表最多 100 条。
  • p95 延迟、峰值登录量、审计保留期在状态转 Accepted 前定稿。

核心正常与失败流程

登录与常驻图形验证码

  1. 登录页打开即调用无请求体的 POST /auth/captcha，取得短期 challenge ID、 后端 PNG 与过期时间；用户刷新图片时重新调用。接口按 IP 限流并返回 no-store。
  2. 匿名客户端提交 account、password、captchaId 与 captchaAnswer。验证码 HMAC 校验和单次消费在 Redis 原子完成；错误、过期或已消费返回 422 captcha-invalid。
  3. 验证码通过后，Auth 检查账号/IP 风险桶并验证密码；账号格式不符、不存在、禁用、已删除和密码错误 对外保持同一 401 invalid-credentials，未知账号仍执行固定 dummy hash。 每次提交后 challenge 均不可复用，Web 在再次提交前取得新 challenge。
  4. 服务预生成 Session ID、Refresh secret 与 access token；关键 Redis 操作完成后，在 PostgreSQL 事务中创建 Session、更新 lastLoginAt 并写登录审计。事务失败时 token 从不交付。
  5. 返回 access token，并设置 host-only、Secure、HttpOnly、SameSite、最小 Path 的 Refresh Cookie。 Web 只把 access token 放内存。

管理员创建或重置的密码可立即用于正常登录，不存在首次登录强制改密状态。用户可随时调用 POST /users/me/password 主动修改；成功后递增安全版本、清除 Refresh Cookie， 并要求用新密码重新登录。

刷新、并发与重放

  1. 登录、验证码、Refresh 与退出的浏览器请求必须携带精确允许的 Origin，缺失或不匹配均拒绝， 并校验 Fetch Metadata；带 body 的登录要求 JSON Content-Type，空 body 的验证码、Refresh 与退出不要求。SameSite=None 必须另加 CSRF token。
  2. 解析并限制 token 长度、验证 Session UUID、执行 Redis 的 session+IP 限流。
  3. 预生成新 Session/token，在事务中用“旧 Session 未撤销 + 摘要匹配”条件更新，创建同一 familyId 的新 Session 并写轮换审计；并发只有一个请求成功。
  4. 记录前序摘要与轮换时间。短并发宽限窗内的失败者返回 409 + Retry-After，不清 Cookie、不撤销 family；Web 等待后用浏览器中胜者设置的新 Cookie 重试。超出宽限窗再使用旧 token 才判为重放。
  5. 确认重放时只撤销对应 Session family，写重放审计与短期 Redis 标记；不误伤其他设备会话。

管理员修改、重置与软删除

  1. 全局认证与粗权限通过；UserModule 在 actor scope 内读取目标。
  2. 校验 Actor/Target 矩阵、自操作规则和 If-Match。版本冲突返回 412。
  3. 事务开始后重新读取并锁定 Actor 的 role/status/securityVersion 与目标当前状态，再次校验矩阵； 条件更新同时约束 Actor 仍 ACTIVE 且未变更。随后写用户/凭证、递增资源版本；角色、状态、重置密码或删除同时递增 securityVersion；写脱敏 before/after 审计。
  4. 删除写 status=DELETED 与 deletedAt，不物理删除。目标已是 DELETED 且仍在 Actor scope 时，终态优先于旧 ETag，重复 DELETE 返回 204；未知或不在 scope 内返回 404。

唯一超级管理员自动初始化

  1. 独立 bootstrap job 在 Prisma schema migration 后、API 启动前读取 bootstrap secret；应用启动和公开 API 都不执行创建。
  2. 使用数据库条件唯一索引保证最多一个 SUPER_ADMIN；advisory lock/串行化事务先检查 ACTIVE SUPER_ADMIN。已有 ACTIVE 超级管理员时安全 no-op，不改密、不覆盖，也不因缺失 bootstrap secret 失败。
  3. 用户库为空且没有 ACTIVE 超级管理员时，两个 bootstrap 变量必须同时存在，才创建配置账号、凭证和脱敏审计。 若存在任意 USER/ADMIN、禁用或已删除的超级管理员、配置账号冲突，或任一变量缺失，job 失败且绝不提升、覆盖或修改既有账号。
  4. 显式提升 ACTIVE ADMIN 仅用于受控恢复；首次初始化不依赖它。生产 secret 由部署环境注入，禁止写入版本库、日志或审计明文。

Problem Details

统一 application/problem+json，包含稳定 type、title、status、detail、 instance、requestId。新增稳定类型：captcha-invalid、 precondition-failed。不返回 stack、SQL、凭证、Cookie 或账号存在性。

校验边界

拒绝未知字段；account trim/lowercase 后匹配 ^[a-z0-9][a-z0-9._-]{4,31}$，密码 12–512，displayName trim 后 1–120； 角色/状态使用枚举。 密码 OpenAPI 使用 minLength 与 YAML 单引号 pattern，避免现有 0001 的反斜杠转义歧义。

并发与排序

  • 资源响应返回整数 version 与强 ETag；PATCH/DELETE/password-reset 要求相同资源 ETag。
  • 事务内重读 Actor 与目标；更新条件包含 id + version + actorId + actor securityVersion + actor ACTIVE + actor 可管理目标。零行区分 404、412 与权限失效，但不泄露越权目标。
  • 列表默认 createdAt desc, id desc；opaque cursor 包含最后键、排序与筛选指纹，篡改返回 400。
  • 搜索只匹配规范化 account/displayName，输入最长 120；排序字段白名单，不接受任意 SQL 字段。
  • 创建依赖 normalizedAccount 唯一约束，重复返回 409；软删除后账号仍不复用。

HTTP 边界

CORS 精确 origin，methods 包含 DELETE，allowed headers 包含 Authorization/Content-Type/If-Match， exposed headers 包含 ETag/Location/Retry-After；JSON body 设上限；启用安全头与 shutdown hooks。 TRUST_PROXY 只在可信反向代理网络启用，不能无条件相信客户端转发头。

日志与指标

日志关联 requestId、actorId、sessionId、action、result，不记录凭据。指标至少覆盖登录结果、 captcha invalid、限流、鉴权 401、授权 403、版本 412、审计失败和 Refresh replay。

健康与运维

/health 只表示进程；/ready 检查 PostgreSQL/Redis。生产探针走内部网络， 不注册运行时 Swagger/OpenAPI 路由。过期 Session 与审计保留由上线 runbook 定义，不预建业务 Scheduler。

实施、迁移、回滚与验收

  1. 阶段 0 — 合同冻结（已完成）： ADR-0008、权限矩阵、登录标识、验证码 TTL/限流和消费者边界已冻结。当前无外部消费者；未来若出现独立消费者， 只能从 /api/v2 新建兼容窗口，不能回写旧邮箱契约。
  2. 阶段 1 — Expand schema（已实施）： migration A 添加 SUPER_ADMIN/DELETED 枚举值。已有用户库先由 prepare-legacy-accounts 在串行化事务中锁表，按显式 userId → account 映射填充 nullable account/normalizedAccount；禁止从邮箱推导。migration B 复验完整性、格式和唯一性，再收紧 NOT NULL， 并回填 Session family/absolute expiry。无法可靠回填的遗留 Session 统一撤销。
  3. 阶段 2 — 安全代码（已实施）： 全局 Guard、显式 Public allowlist、目标级策略、自定义账号、常驻验证码、Session family 与 DTO 回归已落地； service-web 按 0002 Implemented 合同协同发布。运行时不注册 Swagger/OpenAPI 路由，避免匿名绕过。

  5. 阶段 4 — Contract 状态（已完成）： 0002 已设为 Implemented，0001 已设为 Superseded；0001 只保留为历史和 legacy 数据迁移参考。

回滚

激活前

回滚镜像，保留扩展

回滚应用与 Web；保留 nullable 列和未使用 enum 值。PostgreSQL enum 不执行破坏性删除。

激活后

激活后禁止回滚旧鉴权镜像

阶段 3 首次写入 SUPER_ADMIN/DELETED，或签发依赖 family/absolute expiry 的 Session 后即越过 point of no return。旧 Guard/会话逻辑会丢失角色层级或绝对期限，并可能重新启用软删除账号； 故障只能 roll forward，或部署兼容修复镜像。

数据恢复

软删除不自动反转

应用回滚不恢复已删用户或旧密码。需要恢复时走受审计运维命令；保留数据库备份，不执行 down -v。
