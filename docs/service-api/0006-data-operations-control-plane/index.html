Apex · service-api · Technical solution · 0006

数据运维公开控制面

在现有默认拒绝鉴权、固定三级角色、PostgreSQL 审计和 DataSyncModule 防腐客户端之上，增加 POST-only 数据运维 API。 API 只负责身份、授权、可靠投递与脱敏投影；数据目录、命令、运行、健康、计划和全局单运行锁 始终由 service-data-sync 权威持有。

问题

现有 API 只读 data-sync，缺少手工同步、健康检查、动态计划、交付对账与运维记录。

选择

新增 DataOperationsModule；所有写意图同事务落 Submission、HTTP Outbox 与 AuditLog。

理由

跨库无法原子提交；本地 outbox 加下游幂等账本可防丢失、重复执行和伪造同步锁。

主要风险

首次写入只证明本地意图已持久化；实时 capability、资源状态和计划资格 可能在 dispatcher 投递后异步 REJECTED。

现状事实与约束

已验证事实

认证默认拒绝，角色固定

DefaultJwtAuthGuard 与 RolesGuard 已全局注册； 每次受保护请求复验 PostgreSQL Session、ACTIVE User、角色和 securityVersion。角色只有 USER、ADMIN、SUPER_ADMIN。

已验证事实

审计有权威存储与脱敏读取

AuditLog 保存 actor、action、target、requestId、JSON metadata 与时间； 安全审计详情只经过服务端 action registry。在线保留 90 天，当前完整安全审计只允许 SUPER_ADMIN 读取。

已验证事实

DataSyncModule 当前只读

现有客户端使用专用 Bearer、硬超时、请求关联和 Zod schema 校验，网络或合同漂移映射为 503；没有同步任务、Provider SDK、同步库凭据、统一重试、熔断或命令 outbox。

已验证事实

API PostgreSQL 不含同步事实

Prisma 当前只有 User、Credential、Session 与 AuditLog。API 不拥有 canonical dataset、publication、run、健康结论或自动计划。

已验证事实

浏览器边界已有基础

CORS 只允许配置的单一 Origin、credentialed POST 和固定 header；全局 ValidationPipe 拒绝未知字段。当前 allow-headers 尚未包含 Idempotency-Key。

关键缺口

不能靠 API 判断“当前无任务”

多 API 实例、CLI、scheduler 和 worker 都可能竞态。全局串行权威必须在 data-sync PostgreSQL 执行槽、租约与 fencing token 中实现，API 不能另建锁或缓存锁。

跨服务基线 本方案遵循 ADR-0002、 ADR-0008、 ADR-0018 与 ADR-0019。 API 不读取 data-sync PostgreSQL、对象存储或 Provider；Web 不绕过 API。

目标、非目标与能力卡

目标

  • 查询数据资产、双层来源、观测与新鲜度、命令批次、运行、质量门、健康与计划。
  • 可靠提交单个/批量同步、取消、重试、主动健康检查和计划变更。
  • 对每个主动操作保留操作者、理由、授权、交付和权威执行结果关联。
  • 下游暂不可用时不丢意图、不重复命令，并可从 PENDING 对账到终态。

非目标

  • API 持有同步全局锁、run、计划或质量事实。
  • API 在 outbox 前复制或预判实时 capability、计划资格、资源存在性或可重试状态。
  • API 直连同步库、对象存储、AKShare、Tushare 或进一步来源。
  • 浏览器传任意 task 名、Provider 参数、Python 表达式、SQL 或原始 cron。
  • v1 删除计划、回滚 publication、切换来源、强杀 worker 或查看 raw 失败载荷。

规划容量与 SLO

  • 公开 JSON body ≤ 64 KiB；响应 ≤ 2 MiB；批量目标 ≤ 100。
  • 健康下游时只读请求 p95 ≤ 1 s；总 deadline ≤ 5 s。
  • 本地持久化 submit p95 ≤ 300 ms，不等待下游。
  • 下游健康时 99% Submission 在 30 s 内完成交付；队列等待不计交付延迟。

双层授权

Controller 用 @Roles() 做粗粒度拒绝；DataOperations use case 再检查 actor ACTIVE、action、DTO/大小、限流、公开幂等和 preflight 引用形状。它不查询或复制 catalog capability、 schedule eligibility、COMMAND/RUN 状态。data-sync 只信任专用 service identity 携带的 opaque actorRef 和 role snapshot，不信任浏览器字段。

权限与 securityVersion

/users/me 增加固定 data-operations permission。只增加代码映射不批量递增 securityVersion；用户角色变化、禁用或删除仍按现有事务递增并立即使旧 token/session 失效。 Web 权限显隐不是授权依据。

理由与最小化

所有写操作要求 2–500 字理由。API 传递 actorRef、role、reason、submissionId、requestId； 不传用户 JWT、账号、邮箱、Session ID、密码、Cookie、Provider secret 或原始请求头。

CORS、CSRF、Cookie 与代理

  • data-operations 使用 Authorization Bearer，不使用 Refresh Cookie 作为业务授权；即使浏览器自动携带 refresh cookie，它也不能授权任一运维 route。
  • 写操作仅接受 application/json。浏览器请求必须精确匹配配置的 Origin，并通过 Sec-Fetch-Site same-origin/same-site 检查；跨站与缺少 Bearer 的请求统一拒绝。
  • CORS 继续只声明 POST；allowedHeaders 增加 Idempotency-Key， 保留 Authorization、Content-Type、X-Request-Id；响应暴露 X-Request-Id、Location、 Retry-After。框架处理 preflight，不注册 OPTIONS Controller。
  • 非浏览器自动化若未来开放，必须使用独立主体与契约，不通过放宽浏览器 Origin 校验复用个人 JWT。 TRUST_PROXY 继续显式配置，禁止无条件信任转发头。
  • 读取响应与 Submission、操作记录统一 Cache-Control: no-store；Web 可按页面策略保留 TanStack Query 内存缓存，但退出或权限变化必须清除。
防滥用边界 应用层对 actor + action 使用短 TTL 安全计数；写操作初始上限建议 10 次/分钟，preflight 30 次/分钟，读取 120 次/分钟。计数不是任务状态；Redis 不可用时写操作 fail closed。 data-sync 仍以队列深度、Provider 预算和 dataset capability 作第二道容量限制。

输入和分页边界

未知字段拒绝；cursor 最长 1024 字符；公开 page limit 1–100；目录 domain/provider/ upstreamSource 各最多 20；其他 dataset filter 与批量 target 最多 100；理由 2–500 字。/runs/detail 直接复用 RunDetailRequest：partitionsCursor/partitionsLimit 与 timelineCursor/timelineLimit 可独立或同时续页，limit 默认 100、最大 200；响应给 partitionCount/partitionsNextCursor 与 timelineEventCount/timelineNextCursor，partitions、timeline 各最多 200。目录 sourceBindings 最多 10，detail healthRules 最多 200，preflight warnings 最多 20；health detail 的 issuesCursor/issuesLimit 独立分页，limit 默认与最大值均为 100， currentOpenIssues 最多 100。日期使用 RFC 3339 或 ISO date； 响应完整解析后才返回，最大 2 MiB，超限不截断成伪完整响应。

来源、观测与时间字段

每个 source binding 同时给 providerId、upstreamSource、sourceDataset、adapter、 methodology、approval 与 PRIMARY/FALLBACK/SHADOW。availability 使用 ENABLED/DISABLED/SOURCE_UNAVAILABLE/UNKNOWN，并与 observationState 分开；后者明确 PRESENT、EMPTY_VALID、 EMPTY_UNEXPECTED、NOT_YET_SYNCED、UNKNOWN，二者分别携带稳定 availabilityReasonCode/observationStateReasonCode。RunDetail 另投影 受理时冻结的 sourceSnapshot；禁止用当前目录来源改写历史。 sourceBindings 与 sourceSnapshot 均最多 10 项。

DatasetTiming 与 freshness

显式投影 lastAttemptStartedAt / lastAttemptFinishedAt / lastAttemptStatus、lastSuccessAt、lastPublishedAt、 dataAsOf/Kind/Label、coverageFrom/To，以及 freshnessStatus、lag value/unit、reasonCode、evaluatedAt。Web 不从 run success 或日期自行推导新鲜度。MODEL_ONLY 数据集明确 freshnessPolicy=null、dataAsOfKind/freshnessStatus=NOT_APPLICABLE； 合同 oneOf 同时保证 freshnessPolicy=null 当且仅当 freshnessStatus=NOT_APPLICABLE；非 null policy 的状态只能是 FRESH/WARNING/STALE/UNKNOWN。Web 显示“不适用”，不得当成缺配置或 UNKNOWN。

健康评估与 ingestion quality gate

HealthEvaluation 是按 dataVersion/policyVersion 固化的不可变事实， 含 nullable healthCheckId；主动检查产生时可反查批次，自动发布后评估为 null。search 的 HealthEvaluationSummary 只返回评估标识、状态、分数、 evaluatedAt、规则计数、affectedRecordCount，以及查询时 currentOpenIssueCount/issueProjectionAsOf，不含逐规则 results。detail 请求直接引用 0022 HealthDetailRequest，以 evaluationId 加可选 issuesCursor/issuesLimit 续取当前 issue，limit 默认/最大 100；响应 HealthDetail 组合 immutable evaluation 与 currentOpenIssueCount/currentOpenIssues/ currentOpenIssuesNextCursor/issueProjectionAsOf。不可变 evaluation 内的规则 results 最多 500 条，规则保留 INFO/WARN/CRITICAL severity，以及 PASSED/WARNED/FAILED/UNKNOWN/SKIPPED 的规则 status、 expected/observed、affectedCount 与脱敏 sampleSummary；当前 issue 最多 100 条，只含 OPEN/ACKNOWLEDGED 与安全 evidenceSummary，不含原始记录或 Provider 正文。RunDetail 的 qualityGate 独立返回 NOT_EVALUATED/PASSED/WARNED/BLOCKED、policy code/version、 受影响数与安全错误。发布后 CRITICAL 不撤销 publication； 发布前 BLOCKED 才阻止新版本发布。

同步模式、preflight 与自动计划

人工 supportedModes 可声明 FULL、INCREMENTAL、 DATE_RANGE、OBSERVATION_DATE，也可在 manualEnabled=false 时为空；独立 scheduleSupportedModes 只允许 FULL、 INCREMENTAL、OBSERVATION_DATE。range 含两端，snapshot 只用 observationDate。每个同步 target 还必须携带受 DatasetCapability.selectorKinds 约束的严格业务 selector； 它覆盖 GLOBAL、证券、板块、交易所、合约及既有专项入口，但不接受 Provider 参数、URI、凭据或任意 JSON。preflight 依赖 data-sync，停机返回 503；submit 只校验 preflightId/requestHash/targets 的引用形状。targetPolicy 必填 policyVersion，前两种计划模式 dateResolution=NONE， 观察日只能选计划本地日期或最近完成交易日。公开 capability 同步投影 scheduleTargetPolicyOptions；每项包含 mode、版本化 policy 与 isDefault。新建计划表单按所选 mode 过滤选项，以该 mode 唯一 isDefault 初始选中，并原样提交 policy；不得由 mode 自行猜测日期解析规则。scheduleEligible=false 时选项必须为空；否则 scheduleSupportedModes 中每个 mode 至少一个选项且恰有一个默认项。 ScheduleUpsertRequest 以 scheduleId/expectedVersion 成对判别 create 或 update： create 两者同为 null，update 两者同为非 null；半空组合是本地结构错误， 同步返回 422 且不得创建 Submission/Outbox。v1 以 datasetCode 作为计划唯一绑定：每数据集最多一条； 重复 create 由 data-sync 返回 409，update 不得把 scheduleId 改绑到其他 datasetCode，Web 编辑时固定数据集字段。计划同样冻结一个允许的 selector，API 只将其安全 规范化后写入 Outbox，不自行解释为 Provider 调用。

健康检查批次对账

HEALTH_CHECK_SUBMIT 被权威服务受理后，Submission.authorityResource 固定为 HEALTH_CHECK(healthCheckId)，queuePosition=null。reconciler 用新增内部 /health/checks/detail 轮询批次状态；公开 /health/checks/detail 保持 targets 原提交顺序，把 actorRef 投影为 requestedBy ActorDisplay，并返回每个目标的 resolvedDataVersion、status、evaluationId 与安全 error。目标结果按 status 机器约束：SUCCEEDED 必有 resolvedDataVersion/evaluationId 且 error=null；FAILED、REJECTED 必有 error，REJECTED 的 resolvedDataVersion=null；排队、运行、取消分支也固定 nullable 字段，Web 不凭空组合状态。成功评估再以 HealthEvaluation.healthCheckId 反查所属主动批次。

公开 timeline、checkpoint 与 ErrorSummary

RunDetail.timeline 只使用公开 OperationEventView；事件 actor 必须是 ActorDisplay，禁止透出 actorRef；result 完整保留 CANCEL_REQUESTED、INTERRUPTED、SKIPPED 等权威状态。内部 partition checkpoint 仅返回 kind、positionHash、updatedAt 的有界脱敏摘要；公开 partitions 不含 checkpoint。ErrorSummary.stage 固定为 PREFLIGHT、QUEUE、DELIVERY、PROVIDER_FETCH、NORMALIZE、QUALITY_GATE、 HEALTH_EVALUATION、PERSIST、PUBLISH、CHECKPOINT、SCHEDULE、CANCEL、 RECOVERY；API 只投影 code、stage、retryable 与安全 message。

公开投影完整保留八种 CommandStatus：QUEUED、RUNNING、 CANCEL_REQUESTED、SUCCEEDED、PARTIAL、FAILED、CANCELLED、 REJECTED。CommandDetail 在命令创建 child 前即被 REJECTED 时允许 childRuns=[]；其余已受理命令至少一个 child，且始终按原 target 顺序返回。九种 RunStatus 则为 QUEUED、RUNNING、 CANCEL_REQUESTED、SUCCEEDED、PARTIAL、FAILED、CANCELLED、 INTERRUPTED、SKIPPED；总览中的 ExecutionSlot 也完整保留 IDLE、RUNNING 与 RECOVERING，API 不合并或猜测这些权威状态。合同 oneOf 规定 IDLE 时 runId/datasetCode/leaseUntil/heartbeatAt 全为 null；RUNNING 或 RECOVERING 时四项全为非空的权威执行上下文，Web 不从残缺字段自行推断槽位。

COMMAND 与 RUN 作用域 COMMAND 取消会直接取消未开始 child，并对活跃 child 发起合作式取消； COMMAND 重试只复制可重试的 FAILED、PARTIAL 或 INTERRUPTED child。RUN 只作用一个子运行，不得误伤或重建整批。API 仅校验 resourceType/resourceId 形状，资格和终态由 data-sync 在 dispatcher 投递后裁决。
取消动作结果不等于 target 终态 只有权威 target 最终为 CANCELLED，才算取消达成。若取消意图已受理但执行过晚， deliveryStatus 可保持 ACCEPTED，Submission/OperationRecord 的 operationResult 投影 FAILED，并返回稳定 ErrorSummary(code=cancel_too_late, stage=CANCEL)。authorityResource 仍指向原 target；该 COMMAND/RUN 可以真实完成为 SUCCEEDED，Web 必须允许跳转查看， 不得把目标状态改写为取消失败。
CommandReceipt 同时描述新命令与原目标 data-sync 受理回执固定返回 commandId、submissionId、status、target、 targetStatus、childRunIds、queuePosition 与 acceptedAt。submit 的 target 固定为新 COMMAND(commandId)，且 targetStatus=status。cancel 的 commandId/status 描述被取消 RUN 所属或被取消的 parent command； target/targetStatus 描述实际目标。retry 的 target/targetStatus 仍描述原 COMMAND 或 RUN，而 commandId/status 与 childRunIds 描述新建、可追溯的 retry command，API 不把原目标状态误投影成新命令状态。合同 oneOf 按 target.resourceType 机器约束 targetStatus：COMMAND 只能引用 CommandStatus，RUN 只能引用 RunStatus；后者可为 INTERRUPTED 或 SKIPPED，顶层 status 只使用上述八种 CommandStatus。queuePosition 在 submit/retry 回执中表示新命令首个 child run 的受理事务快照位置；cancel 为 null，其余 child 的位置从 commands/detail.childRuns 读取。
ActorDisplay 先区分 USER 与 SYSTEM USER 的 systemKind=null；用户删除后可隐藏 actorId，以 deleted=true、displayName=“已删除用户”投影。SYSTEM 固定 actorId=null、deleted=false，并以 systemKind 区分 SCHEDULE、LEGACY、RECOVERY、OTHER；前三者分别显示“系统计划”“遗留任务”“系统恢复”。 系统 actor 永不误标为已删除用户，command/run requestedBy 与 OperationRecord.actor 复用同一映射。

202 的唯一含义 授权意图、HTTP Outbox 和安全审计已经在 API PostgreSQL 同一事务提交。 首次创建的任一主动写都必须返回 deliveryStatus=PENDING、queuePosition=null； HTTP 请求线程不得在提交后 immediate/best-effort 直投，唯一投递者是独立 dispatcher。 示例 Submission 首次创建后，服务端冻结 downstreamIdempotencyKey=dataops:45ea5915-3184-4491-8181-18026c8a6f34； 该内部 key 不返回浏览器。 只有 deliveryStatus=ACCEPTED 且出现 authorityResource，才表示 data-sync 权威账本已经受理；queuePosition 不是通用受理标志，cancel、健康检查、计划动作仍为 null。运行成功仍必须等待 operationResult。
authorityResource 按 action 固定映射 PENDING 一律为 null。SYNC_SUBMIT 与 SYNC_RETRY 接受后指向新 COMMAND(commandId)；SYNC_CANCEL 指向原 target 的 COMMAND 或 RUN； HEALTH_CHECK_SUBMIT 指向 HEALTH_CHECK；SCHEDULE_UPSERT 与 SCHEDULE_SET_ENABLED 指向 SCHEDULE。Submission 与 OperationRecord 使用同一映射，Web 只据此跳转权威资源。接受后的 queuePosition 只有 SYNC_SUBMIT/SYNC_RETRY 非空，且指向新命令首 child 的受理事务快照位置；cancel、健康、计划与所有未受理交付均为 null。
Submission 与操作记录都是机器状态机 SubmissionReceipt 的 deliveryStatus oneOf 拒绝非法组合： PENDING/DELIVERING 只能是 UNKNOWN 且无 authority/queue；REJECTED 必为 operationResult=REJECTED，DEAD_LETTER 保持 UNKNOWN，两者均无 authority 且必须有安全 error；ACCEPTED 必有 authority，并再按 action 绑定 COMMAND、原 COMMAND/RUN、HEALTH_CHECK 或 SCHEDULE，只有接受的 submit/retry 可带首 child queuePosition。OperationRecord 同时保证 USER 当且仅当 submissionId 为 UUID 且 deliveryStatus 非 NOT_APPLICABLE，SYSTEM 当且仅当 submissionId=null 且 deliveryStatus=NOT_APPLICABLE；其第二层 oneOf 再约束 pending/delivering 无 authority 与观测时间、accepted 或系统 操作有 authority/lastObservedAt、rejected/dead-letter 的终态时间与错误。

幂等与乐观并发

  • 所有写 route 要求 16–128 字符 Idempotency-Key。唯一作用域是 actorId + key； requestHash 包含 route 与规范 body。同步 submit 只验证 preflightId、requestHash、targets 的 DTO/引用形状，不在 API 复验 preflight 时效、实时 capability 或来源状态。
  • 同 actor、同公开 key、同 hash 返回原 Submission，不新写 outbox 或审计，并继续复用已冻结的内部 key；同公开 key 异 hash 返回 409 idempotency-key-reused。key 与 Submission 终态至少保留 90 天。
  • 首次创建 Submission 时，以 submissionId 确定性派生 dataops:<submissionId>，作为 downstreamIdempotencyKey 与规范内部 body 一起冻结到 Outbox。不同 actor 即使使用相同公开 key，也得到不同内部 key。
  • dispatcher 每次尝试都传原下游 key 与原内部 body。网络断开、timeout 或 5xx 后禁止生成新内部 key，防止 data-sync 已受理但 API 未收到响应时重复命令；公开 key 绝不原样透传到 data-sync。
  • schedule 创建要求 scheduleId/expectedVersion 为 null；更新要求两者同为非 null，启停要求 scheduleId 与当前 expectedVersion。半空 upsert 组合在 DTO 阶段返回 422，不进入 outbox。结构合法写入后，版本由 data-sync 在单事务中比较并递增；异步冲突令 Submission 进入 REJECTED，错误码 schedule-version-conflict，Web 必须刷新后重做，不自动覆盖。API 不在 outbox 前查询 datasetCode 是否已有计划；重复 create 或 update 改绑由 data-sync 返回权威 409， 再异步投影 REJECTED。

部署决策

同镜像、独立 dispatcher 进程

新增 pnpm data-operations:dispatch 入口和独立部署实例，不在 HTTP 请求进程内启动无限 poll。可运行多个副本；PostgreSQL lease 与 SKIP LOCKED 防重复领取。它是唯一投递者；请求进程不做 post-commit 直投。无需 BullMQ、跨服务事件平台或业务 Redis。

重试决策

只对冻结下游 key 的 mutation 重试

full-jitter 指数退避初值 1 s、上限 5 min；429 遵守 1–300 s Retry-After。 400/404/409/422 是业务终态；内部 401/403 立即 DEAD_LETTER 并触发凭据事故告警。重试、对账和 replay 均不得换内部 key。

人工恢复

原 outbox replay，不重新授权

Contract 0023 v1 不开放浏览器 replay route。受控 runbook 校验 ACTIVE SUPER_ADMIN、 submissionId 与明确确认值，只把原 DEAD_LETTER 行重置为 PENDING，并追加 dataops.delivery.replayed 审计。

不是跨服务事件平台 HTTP Outbox 只解决 API PostgreSQL 提交后到一个 data-sync 内部 POST 的可靠交付。 它没有订阅者、广播、顺序分区或通用 schema registry；未来引入事件平台必须另建 ADR。

所有写操作统一入口

SYNC_SUBMIT、SYNC_CANCEL、SYNC_RETRY、HEALTH_CHECK_SUBMIT、SCHEDULE_UPSERT、 SCHEDULE_SET_ENABLED 全部使用同一 Submission/Outbox 模板。禁止某些 route 直接同步调用下游、 另一些 route 走 outbox；否则审计、未知结果和故障恢复语义会分裂。

事务边界

  1. Guard/用例只完成身份、RBAC、Origin、DTO、64 KiB、限流、公开幂等和 preflight 引用形状；规范化 body 与 action 后计算 requestHash。reason 仅 trim，不记录不可控 header。不得在此查询实时 capability、schedule eligibility、resource existence 或 version。
  2. Prisma 事务尝试插入 Submission。唯一键冲突时读取既有行：hash 相同返回原资源，hash 不同返回 409。
  3. 首次插入时用 submissionId 派生 downstreamIdempotencyKey，再在同一事务写冻结该 key 与规范内部请求的 Outbox，以及 dataops.request.authorized AuditLog。 AuditLog 写失败必须使 Submission 和 Outbox 一起回滚；提交后直接返回 PENDING。
  4. 只有独立 dispatcher 可领取 lease 并执行内部 HTTP；请求进程没有 immediate/best-effort 投递分支，且 dispatcher 不在持有数据库事务时等待网络。
  5. 每次交付终态在一个短事务内更新 Outbox、Submission，并追加 accepted/rejected/dead-letter 审计。reconciler 只更新明确标为 projection 的字段。

/data-operations/operations/search 是运维投影，不等同 /audit-events/list。前者允许 ADMIN/SUPER_ADMIN 查看 data-operations 动作、authorityResource、lastObservedAt 与 data-sync 执行结果；后者仍是 SUPER_ADMIN-only 完整安全审计入口。command/run 详情的 requestedBy 与 OperationRecord.actor 均投影为 ActorDisplay： USER 通过非空 submissionId/actorRef 联结 Submission 与 User；系统计划、 legacy、recovery 无 API Submission，submissionId=null、 deliveryStatus=NOT_APPLICABLE，并按 systemKind 显示系统身份。永不透出内部 actorRef，也不把系统 actor 显示成“已删除用户”。

迁移、backfill 与回滚

  • 独立 Prisma migration job 新增 enum、两张表、FK、唯一约束与索引；生产 API 启动不执行 migration。 新表为空，不需要历史 backfill。
  • expand 后旧 API 完全忽略新表；先部署理解新 permission 的 Web，再部署 API DTO/只读 route， 最后部署 dispatcher 与写 route。
  • 回滚先关闭 data-operations 写 feature gate，再停止 dispatcher；保留 Submission、Outbox 与 AuditLog。 已被 data-sync 接受的 command 不撤销、不删除、不改写为失败。
  • Prisma/PostgreSQL enum 不做破坏性移除。已有 Submission 后只允许 roll forward 修复； 回滚脚本只删除确认从未启用且为空的新表。

故障不变量

data-sync 停机

catalog/command/run/health/schedule 读取和 sync preflight 返回 503；已持有 preflight 引用的 submit，以及取消、重试、健康检查和计划 等结构合法写仍可在 API PostgreSQL 落为 PENDING。API readiness 不因下游停机而重启风暴；outbox oldest age 告警。

API PostgreSQL 停机

写操作不得返回 202，因授权、outbox 和审计均未持久化；读取 data-sync 的 route 也按 ready policy fail closed，避免身份/审计边界不完整。

接受响应丢失

Submission 保持 PENDING；dispatcher 用原下游 key 重试。data-sync 在 caller service + 内部 key 域内，同 key 同 hash 返回原 command receipt，因此最多一个权威 command。

合同拒绝

data-sync 400/404/409/422 更新 Submission 为 REJECTED，并保留安全 code。这是 dispatcher 交付后的异步权威结论，不改变初次 HTTP 202/PENDING。公开 cancel、retry 与 schedules/set-enabled 不把下游 404 改写成同步公开 404。用户刷新 capability/preflight/version 后提交新意图与新 key；旧意图不可改写。

重复 dispatcher

lease 限制领取，但网络延迟或进程暂停仍可能重复 POST；正确性依赖 data-sync idempotency inbox，不依赖“理论上只发一次”。

对账漂移

ACCEPTED 超过 5 分钟仍查不到 authority resource、终态超过 2 分钟未投影、lastObservedAt 过期或状态回退时告警。API 以 data-sync 重新同步 authorityResource/operationResult 投影，不反向修正权威事件。

回滚

先停写，再停 dispatcher

关闭写 feature gate、隐藏 Web 动作、停止 outbox dispatcher；只读可保留。保留所有 Submission、Outbox、AuditLog 和已受理 data-sync command。不得清库后重新提交。
