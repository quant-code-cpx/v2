Technical solution · service-api · 0003

板块行情 API 访问技术方案

为已发布的行业、概念板块目录和日/周/月原生行情建立受版本保护的读取链路： service-api 只经 service-data-sync 的内部 HTTP 契约读取， 对外提供认证后的稳定查询接口，不共享数据库、不暴露 raw 证据、不派生日周月数据。

1. 摘要

问题

同步结果尚无服务接口

板块三周期数据已进入同步服务，但 service-api 没有业务模块、下游 client 或公开路由。

决策

内部 HTTP + API 投影

同步服务拥有 canonical 数据和版本；API 通过版本化 internal contract 读取，再投影为 /api/v1。

主要风险

鉴权和生产准入未冻结

静态服务凭据、认证读取和关键回归已实现；凭据轮换、来源许可和稳定性仍须在生产治理中完成。

结论 首期提供目录和 K 线只读查询；请求必须明确 scheme、code、period 与日期窗。 不提供分钟数据、板块成份、EOD quote、申万、资金流、跨 scheme 合并、成交量排名或导出任务。

2. 目标、非目标与事实

目标

  • 认证调用方可分页查询 ACTIVE 行业/概念板块。
  • 按 1d、1w、1mo 读取单板块、单版本行情。
  • 返回 ETag、dataVersion、publishedAt 和终态标记。

非目标

  • 不让 API 查询同步数据库、S3 或供应商。
  • 不从日线计算周/月，不填补周期缺口。
  • 不建立 API 自有行情读模型或 Redis 业务缓存。

已知事实

  • 事实 P0 已有三个独立 canonical 周期表与发布版本。
  • 事实 当前 API 只有 User/Auth 模块，没有下游行情 client。
  • 待决 服务凭据、最终权限和生产 SLO 未定。

3. 功能边界与所有权

service-data-sync

Canonical owner

职责：验证、版本化并发布 sector 数据；提供内部只读投影。

输入 / 输出：canonical publication → internal JSON + ETag。

状态：板块身份、三周期 revision、dataVersion、raw evidence。

失败边界：数据未发布、读库或服务凭据失败时拒绝，不返回 raw 或猜测值。

service-api

Public projection owner

职责：用户认证、授权、输入边界、下游调用、Problem Details 和防滥用。

输入 / 输出：浏览器/API 调用 → internal client → 公共 JSON + ETag。

状态：无行情权威状态；只保留已有用户/会话与短期安全限流。

失败边界：下游错误映射为受控 503，不泄漏 URL、凭据、SQL 或 provider 字段。

service-web / consumer

调用方

职责：显式传入分类体系和周期，按 ETag/dataVersion 处理刷新。

输入 / 输出：仅调用 /api/v1/market/*，不访问 internal 路由。

状态：可持有展示缓存，但不能把 provider_native 成交量跨体系相加。

失败边界：503 显示数据暂不可用；不把缺失渲染为零或休市。

service-web / partner
        │ authenticated public HTTP
        ▼
service-api: IndustryModule + DataSyncModule
  ├─ Auth / final market-read policy
  ├─ DTO validation / rate limit / Problem Details
  └─ SectorMarketDataClient  ── service credential ──▶ service-data-sync internal v1

禁止：service-api ── SQL / S3 / AKShare ──▶ service-data-sync owned storage

4. 核心流程

1. 用户请求 POST /api/v1/market/sectors/{scheme}/{code}/bars
2. service-api 全局 Guard 验证 Session；最终 market-read policy 通过
3. DTO 校验 scheme、code、period、包含端 start/end、limit/cursor、If-None-Match
4. DataSyncSectorClient 转发 requestId、ETag 与专用服务凭据
5. service-data-sync 校验服务身份，选择对应已发布 1d / 1w / 1mo dataVersion
6. internal 返回一页；service-api 验证 JSON 结构、过滤内部字段、返回同一语义响应
7. 响应附 ETag 与 private, max-age=0, must-revalidate

发布切换与分页

cursor 绑定 scheme、code、period、日期窗和 dataVersion。发布被替换后，继续使用旧 cursor 返回 409；客户端从第一页重新读取，避免一页内混入两个版本。

下游失败

连接前超时、可重试连接中断可安全重试一次；下游 5xx、超时、schema 不符、断路器打开均返回 503 Problem Details。没有未标记 stale fallback。

5. 契约、数据语义与安全

完整、可机器解析的契约分别归属同步服务和 API 服务：

  • 0005：service-data-sync 板块内部 OpenAPI
  • 0006：service-api 板块公开 OpenAPI
接口身份 / 输入成功结果错误与缓存
POST /api/v1/market/sectors 认证用户；必填 scheme，可选前缀 query、cursor、limit≤100。 ACTIVE 板块目录页、dataVersion、publishedAt。 400/401/403/429/503；ETag 命中返回 204。
POST /api/v1/market/sectors/{scheme}/{sectorCode}/bars 认证用户；必填 period、start、end；limit≤1000。 一个周期、一个 sector、一个 dataVersion 的 periodEnd 升序页。 400/401/403/404/409/429/503；ETag 命中返回 204。

不可混用语义

scheme + code 才是身份；名称不是主键。1w/1mo 是上游直接结果。periodEnd 是上游标签，不是 API 推算的周期起点。

精度与单位

价格、金额、百分比和成交量均以 decimal string 返回，避免 JavaScript 浮点漂移。成交量必须携带 provider_native；禁止跨 scheme 比较、求和或排名。

授权待决 方案提出“现有 ACTIVE 登录用户可读”作为首期候选，最终角色/permission 必须在 ADR-0011 评审后冻结。 任何实现不得通过 @Public() 绕开全局默认认证，也不引入 forwardRef()。

6. 可靠性、运行与兼容

下游 client

小超时、一次安全重试

新增环境配置承载 internal base URL、超时、服务凭据和 retry budget。GET 仅在未写入响应时重试一次；timeout、5xx 和 schema drift 不做 cross-source fallback。

可观测性

双服务关联

透传 X-Request-Id；记录 route、scheme、period、status、dataVersion presence、duration 与 retry，不记录 token、raw URI、payload 或高基数 sector code 指标。

健康

业务失败不重启 API

/health 仍只表示进程，/ready 仍只检查 API 自有 PostgreSQL/Redis。数据同步不可用由 route 503、client 指标和告警表达。

兼容与回滚

  • v1 兼容：仅可新增 optional 字段；改变 scheme、period、decimal 字符串、单位或 cursor 语义必须发布 v2。
  • 部署顺序：先发布 data-sync internal v1 与 contract test，再发布 API client/module；最后按受控流量开放 public route。
  • 回滚：关闭 API 路由或回滚 API client，不删除同步数据、raw 或 publication。已公开 v1 的 internal endpoint 保持兼容窗口，故障优先 roll forward。
  • 不新增数据迁移：API 不增加 Prisma 行情模型；同步服务的 internal 读层使用现有 canonical 数据及后续独立 schema 演进。

7. 方案取舍

候选优点代价结论
同步服务 internal HTTP版本、质量、迁移和所有权清晰。增加网络调用与 503。采用
API 直连同步 PostgreSQL低延迟、短期代码少。共享 schema 和凭据，绕过 publication。禁止
API 自有完整读模型运行时隔离、读性能高。事件、回放、一致性和第二份数据治理。延后；规模证明后另立 ADR
Redis 行情缓存可减少下游读取。容易成为无版本权威副本；当前无需。首期不采用

8. 实施、验收与待决

  1. 阶段 0 — 合同评审：评审 ADR-0011，冻结用户权限、服务凭据、网络边界、timeout/rate limit 和 p95/SLO；未通过不建公开路由。
  2. 阶段 1 — 同步服务读层：实现 internal FastAPI 路由、ACTIVE catalog read port、scheme+code 查找、版本绑定 cursor、ETag、服务鉴权与 contract test。
  3. 阶段 2 — API 投影：实现 IndustryModule、DataSyncModule、DTO、client、Problem Details、授权策略、OpenAPI contract test、日志/指标；不改 Prisma 业务表。
  4. 阶段 3 — 受控发布：先内部调用和 shadow metrics，再开放 public route；验证 401/403、cursor 409、下游 503 和 dataVersion 一致性。

验收标准

  • API 不导入同步数据库 schema、SDK 或 adapter。
  • 同一 response/page 只含一个 period/dataVersion；周/月不读日线。
  • unknown scheme、超界日期、篡改 cursor、PENDING sector 均不泄漏数据。
  • 401/403/404/409/429/503 和 ETag/204 有自动测试。
  • internal/public OpenAPI 可解析，双向 contract test 与 Docker health 通过。

待决问题

  • 服务凭据采用短期 token、mTLS 或受网络限制的静态 secret — 平台/安全评审。
  • 所有 ACTIVE 用户是否可读，或新增 market-data permission — 产品/安全评审。
  • 超时、限流、SLO、历史最大窗与 cursor TTL — 探针和消费流量测量后确定。
  • 来源许可、生产 source policy、volume 标准单位 — data-sync 准入评审。
