高价值市场数据 Canonical Model 与 PostgreSQL 物理设计

1. 结论

问题

新增专题会复制身份、时间和运行账本

八份专题各自需要来源、批次、raw、质量、修订、发布、证券/合约身份与 PIT。 若逐专题复制，会出现多个“当前证券”、多个 data_version 定义和无法统一恢复的 checkpoint。

推荐

共享支撑，事实强类型，发布不可变

保留当前 72 个 Declarative 模型和 13 个 Alembic revision，additive 新增共享根与领域表。 每个 release 固定方法学、来源批次、质量和内容哈希；publication 只移动指针，不原地改事实。

最大风险

“统一”变成静默混算

统一只覆盖身份引用、审计和生命周期协议，不抹平价格/NAV、汇总/明细、观察/生效、 reported/derived、期货真实合约/连续序列等语义差异。

拟议决策 新增 market_entity 作为跨域引用根，并以 market_instrument 只表达可交易对象；同时保留 equity_instrument.security_id 及现有大表外键；现有 equity_instrument.instrument_id 原值成为根表 UUID。ETF、指数、期货、期权以领域扩展表承载， 不让期货/期权进入股票解析器。该选择为 Proposed，实施前应由独立身份 ADR 接受。
选择结论理由拒绝项
数据库延续 data-sync 独占 PostgreSQL 已有 SQLAlchemy/Alembic、双时态、分区和 publication 基线 service-api 直连；跨服务共享 schema
事实形态强类型领域表 + 统一审计清单 金额、单位、空值、约束可由数据库验证 把供应商 JSONB 当 canonical；通用 EAV

2. 目标、非目标、事实与假设

目标

  • 八专题到 dataset、表、身份、时间和 publication 的唯一映射。
  • 给出可落地 PostgreSQL 字段、类型、约束、索引和分区。
  • 兼容当前 72 个 ORM 模型，不重写 13 个历史 revision。
  • 提供 expand/backfill/switch/contract、回滚和验收 SQL。

非目标

  • 不选择或批准具体生产 Provider。
  • 不创建 migration、ORM、任务、配置、OpenAPI 或 Docker 变更。
  • 不冻结 data-sync → service-api 通信契约。
  • 不承诺历史深度、SLA、采购或对外再分发权。

硬边界

  • SDK、URL、供应商字段仅在 Adapter。
  • Adapter 不写 canonical；service-api 不读 data-sync DB。
  • Redis 不保存权威市场数据。
  • 不同来源、方法学、粒度、币种、终态不可静默混算。
分类内容设计处理
事实当前 registry 明确登记 72 个模型；Alembic 有 13 个不可改写 revision。只做 additive 迁移，schema 权威仍是 Declarative 当前态 + Alembic 演进历史。
事实source_batch 已保存 run、partition、raw URI、hash、observed、upstream、adapter 与 schema fingerprint。保留并扩展；多页/多文件 raw 由新 manifest 一对多承接。
事实dataset_publication 已提供分区 current 唯一、dataVersion、quality、effectiveAsOf、knowledgeCutoff。保留公开语义，新增 release FK，不另造竞争 publication。
建议共享 root 只统一引用，不统一领域计算。根表 + 领域子表；资产类别用 composite FK 校验。
假设PostgreSQL 17、btree_gist、对象存储继续可用。实现前以空库升级和扩展权限验证；不满足则门禁 G1。
待决跨资产根身份是否接受、生产来源、保留期和精确分区阈值。保持 Proposed；阈值由 pilot/压测校准，不阻断 DDL 评审。

5.1 对现表的 additive 变化

  • source_batch 新增可空 source_dataset_id，回填完成后对新 capability 设非空应用门；旧行保留。
  • dataset_publication 新增可空 release_id 与 FK；新 dataset 强制非空，旧 dataset 兼容。
  • dataset_publication.data_version 继续是消费者稳定版本；同内容幂等重放复用 release 和 dataVersion。
  • data_quality_issue.snapshot_id 的 equity 专属 FK 不再扩张；新域通过 evaluation/quarantine 关联。
  • 各专题不得再创建独立 source、raw、通用 quality、publication 或 run 表；领域专用质量明细确有强类型需求时可补充。

6.1 发布算法

  1. 规范化后按业务键稳定排序，字段按 canonical 表顺序序列化，生成每行 content_hash。
  2. 按 dataset、partition、methodology 与行 hash 集合生成 release.content_hash。
  3. 若相同 release 已存在，复用它；新 source observation 仍保留，但不新增业务修订。
  4. 质量通过后创建随机 UUID data_version；同 release 的重复发布请求复用既有 dataVersion。
  5. 单事务关闭旧 current publication、插入新 publication、写聚合 components、推进 checkpoint。
  6. 回滚只创建/恢复指向旧 release 的新 publication 记录或受控切回指针；不删除新 release。
三层 PIT 与防未来函数 查询同时应用事实条件（asOf）与知识条件（knownAt），且 knownAt 不得晚于 publication 的 knowledge_cutoff。 MARKET_PIT 应用 effective + public_usable； KNOWLEDGE_PIT 再应用 known range； OPERATIONAL_REPLAY 再限定 publication activation 区间。 日期-only 公告采用版本化“下一可交易时段”保守转换；日历证据不足时从 observed_at 起可见。 后续收益、事后修订、未来成分/换月、后来确认完成值永不回填早期知识切片。

9. 写入顺序、事务、幂等、并发与恢复

1 acquire partition lease + fencing token
2 fetch through DataSourcePort
3 write immutable raw object → source_batch + raw_payload_manifest
4 normalize → normalization_run + typed candidate rows + manifest
5 resolve instrument/date/calendar; conflicts → quarantine
6 execute quality policy → quality_evaluation/result
7 BLOCKED: preserve candidate/quarantine, keep old publication, no checkpoint advance
8 PASSED/WARNED: create/reuse immutable dataset_release
9 one DB transaction:
    lock current publication(dataset,partition)
    close old current → insert new publication + components
    CAS canonical_checkpoint(fencing token)
    mark sync_partition succeeded
10 after commit: emit metrics/audit; consumer sees complete dataVersion
场景事务/锁幂等键恢复结果
正常增量网络与对象存储不持有 DB 事务；发布短事务run request_key；release content uniquecheckpoint 从最后 publication 后继续一个新 dataVersion
同 raw 重跑新 source observation；复用 normalization/release 可由输入 hash 判断batch observation 独立；业务内容 hash 去重无需补偿raw 审计增加，revision/dataVersion 不增加
重复投递同 partition advisory lock + leaserequest_key + partition key后到者读取完成状态不重复发布
并发不同分区锁键 hash(dataset,partition)，可并行各分区独立单分区失败不污染其他分区可 partial run；聚合 publication 冻结 components
worker 僵死lease_until + fencing_token；旧 token 禁写CAS tokenreaper 回收 queued；从 raw/页 checkpoint 续跑旧 worker 无法晚提交
schema drift不进入 release 事务schema fingerprint修 Adapter 后从 raw replayquarantine + 旧 publication
数据库中断事务原子回滚release/publication unique重新执行发布；raw 已归档消费者不见半批
迟到修订关闭旧 known_to，追加 revision；不改旧值业务键 + methodology + content hash重建受影响 release新 knownAt 才可见
回滚锁 current publication；指向旧 release受控 rollback request ID保留错误 release 供审计新 rollback dataVersion 或明确恢复旧版本策略

9.1 写入批量与隔离级别

  • 大表使用 SQLAlchemy bulk DML/COPY staging；禁止逐 ORM 实例 flush。
  • candidate staging 与 publication 分事务；publication 使用 READ COMMITTED + 行锁/advisory lock 即可，身份区间变更使用 SERIALIZABLE 或显式锁顺序。
  • 身份 → release → publication → checkpoint 固定锁序，防止跨域死锁。
  • 单行坏数据只有在 dataset 允许 partial 且契约明确时可隔离后发布；完整快照、指数权重、持股横截面默认整分区 fail closed。
  • 删除语义使用生命周期/撤回 revision 或 publication 替换，不物理删除历史事实。

龙虎榜/大宗数万–数十万证券/日期/原因；逐笔规模trade_date 年分区；security+date；venue+date大宗经济字段不唯一，必须保留 occurrence
衍生品日行情/期权链数百万，期权为主合约序列；日链横截面trade_date 年分区；contract+date；underlying+expiry+strike达到 2,000 万行/50GB 后再改月分区；避免过早分区

10.1 索引原则

  • 每个线上查询必须命中“身份 + 日期”或“分区日期 + 身份”索引；游标排序尾部包含稳定 UUID/序号。
  • 部分索引只覆盖 current/open knowledge；历史查询用完整复合索引，避免 current 索引误导 PIT。
  • 金额、比率筛选仅对真实高频路由建立部分/覆盖索引；先用 EXPLAIN (ANALYZE,BUFFERS) 证据。
  • BRIN 只用于强时间相关的超大 append-only 分区；不能替代 identity B-tree。
  • JSONB 支撑字段不建通用 GIN；消费者禁止通过任意 JSON 路径访问。

10.2 保留、归档与清理

11. 与当前模型差异、迁移、兼容与回滚

11.1 差异

当前拟议兼容策略不可逆点

11.2 分阶段迁移

  1. M0 冻结证据：从空库执行现有 13 个 revision 到 head；导出 72 表模型、约束、索引、分区、行数与依赖基线。
  2. M1 Shared expand：新增 source/dataset/methodology/raw/normalization/quality/quarantine/checkpoint/release/lineage；现表只加 nullable FK。应用仍走旧路径。
  3. M2 Identity expand：按现有 equity_instrument.instrument_id 回填 root 并校验一一对应；新增 venue/calendar 与新资产领域表。
  4. M3 Domain expand：按 P0 顺序建专题表和父分区；source policy/feature 默认关闭；先 fake/fixture。
  5. M4 Shadow/backfill：只写 raw、candidate、quality、release，不移动 production publication。小窗口、低并发、可暂停。
  6. M5 Read switch：内部读取先绑定 release/dataVersion；双读比对但只有旧路径对消费者权威。通过后原子切 publication。
  7. M6 Contract：稳定窗口后收紧新行 FK/NOT NULL、停止兼容写；旧字段/表只有依赖为零才另案删除。

11.3 回滚矩阵

阶段触发回滚数据处理
M1–M3schema/parity 或应用兼容失败回退应用；新增空表可执行 downgrade旧表不动；确认无引用后才删空对象
M4来源/质量/性能失败关闭 capability，停止 shadow保留 raw/candidate/quarantine；不影响消费者
M5 已发布错误数据、延迟或契约故障publication 指回上一 release；关闭新读取不删 revision/release；修复后 raw replay
M6发现旧消费者恢复兼容 view/client，不恢复双权威写入roll forward；禁止回退到破坏新身份的旧唯一约束
迁移硬规则 production 应用不自动 migration；每个 revision 必须有人工 rollback/runbook。 已产生 production release 后不做破坏性删表降级。历史回补保留真实 observed_at/known_from，不能为了“完整历史”回写早期可见时间。

12.3 验收 SQL

-- 1. 现有 equity UUID 全量映射且无重复
SELECT count(*) FILTER (WHERE m.instrument_id IS NULL) AS missing,
       count(*) - count(DISTINCT e.instrument_id) AS duplicates
FROM equity_instrument e
LEFT JOIN market_entity m
  ON m.entity_id=e.instrument_id AND m.entity_kind='EQUITY';
-- 期望：missing=0，duplicates=0

-- 2. 每 dataset/partition 至多一个 current publication
SELECT dataset,partition_key,count(*)
FROM dataset_publication
WHERE superseded_at IS NULL
GROUP BY dataset,partition_key HAVING count(*)>1;
-- 期望：0 行

-- 3. 新 dataset publication 必须绑定 release，且方法学一致
SELECT p.publication_id
FROM dataset_publication p
JOIN canonical_dataset d ON d.code=p.dataset
LEFT JOIN dataset_release r ON r.release_id=p.release_id
WHERE d.created_at >= :expansion_cutoff
  AND (r.release_id IS NULL OR r.partition_key<>p.partition_key);
-- 期望：0 行

-- 4. checkpoint 不得领先 publication
SELECT c.dataset_id,c.partition_key
FROM canonical_checkpoint c
LEFT JOIN dataset_release r ON r.release_id=c.last_release_id
LEFT JOIN dataset_publication p
  ON p.release_id=r.release_id AND p.superseded_at IS NULL
WHERE c.last_release_id IS NOT NULL AND p.publication_id IS NULL;
-- 期望：0 行

-- 5. knowledge 时间不得早于来源观察
SELECT count(*) FROM normalized_record_manifest n
JOIN normalization_run nr USING(normalization_run_id)
JOIN source_batch b ON b.run_id=nr.run_id
JOIN /* 各 revision 表的统一验收视图 */ canonical_revision_audit v
  ON v.record_key_hash=n.record_key_hash
WHERE v.known_from < b.observed_at;
-- 期望：0；官方历史公开时间只影响 effective/publicUsable，不回填平台 known_from

-- 6. 分区裁剪与索引计划（每个高容量表执行）
EXPLAIN (ANALYZE,BUFFERS)
SELECT * FROM margin_security_daily_revision
WHERE security_id=:id AND trade_date BETWEEN :from AND :to
  AND known_from<=:known_at
  AND (known_to IS NULL OR known_to>:known_at)
ORDER BY trade_date,row_id LIMIT 501;
