1. 摘要

问题

当前 schema 对产品决策不透明

迁移前表结构散落在历史 migration 和约 152 处字符串 SQL 中。维护者无法从一个稳定目录确认当前表、 字段、类型、含义和索引，理解成本已经高于业务可接受范围。

推荐

全量 Declarative ORM

32 张逻辑表一表一模型文件，按业务能力分目录；每个字段显式声明数据库类型、可空性与中文注释； 全部仓储已使用模型字段和 Session。

主要风险

自动迁移不是完整安全网

Alembic 无法可靠自动识别 CHECK、EXCLUDE、重命名和物理分区变化。必须保留显式 migration、 PostgreSQL schema parity 测试与人工审查。

核心结论 没有发现阻止全量 ORM 化的技术障碍。SQLAlchemy 2.0.51 能表达当前主要 PostgreSQL 结构和 DML。 “全量 ORM”现已满足：所有逻辑表都有 Declarative 模型，所有业务仓储通过 Session 与模型表达式访问； 这不代表把历史 migration、extension 或每个月的物理分区伪装成 ORM entity。
0015 完成后的事实校准 0015 已进入 Accepted，四张 EOD 表、动态排行、raw replay、candidate/publish、lease/reaper、 fencing、受控回滚和原子 publication 已形成可执行基线。本文的 32 表、6 个 migration、 6,733 行持久化实现和 152 个 text() 统计已经包含该实现，因此技术选型与迁移范围不变； ORM 阶段必须把这些已验证行为当作回归契约，而不是重新设计 EOD。

2. 目标与边界

目标

  • 打开一个 models/ 目录即可看到同步服务全部逻辑表。
  • 打开单个模型文件即可看到完整字段、类型、含义、主外键、约束、索引和分区策略。
  • 一张逻辑表一个文件；功能相近的表进入同一子目录。
  • 全部仓储从 text() SQL 迁移到类型化模型表达式。
  • 保持现有数据、表名、字段名、事务、幂等、修订、质量门和发布语义不变。
  • 让 Alembic metadata diff、静态检查和架构测试能发现模型漂移。

非目标

  • 不重写或压平已经发布的 Alembic migration 历史。
  • 不改变 provider、市场语义、时区、交易日历、复权、单位或来源许可。
  • 不改变 service-api 通过版本化内部 HTTP 读取的边界。
  • 不把数据库模型暴露为 API DTO 或领域对象。
  • 不依赖 Base.metadata.create_all() 管理生产 schema。
  • 不把所有操作强制转换为逐行对象增删改。

硬约束

  • PostgreSQL 仍是 canonical 权威库；S3 raw evidence 与 Redis 边界不变。
  • 服务继续使用同步 psycopg 驱动和 Docker-only 验证流程。
  • 应用、任务、质量和领域层仍只依赖 port；adapter 仍不得写 canonical DB。
  • 新增和修改定义必须有简体中文职责注释。
  • 迁移过程不得丢失历史修订、来源证据或 publication。

任务定义

业务目的让维护者直接理解同步服务持久化模型，支撑产品与数据范围决策。
消费者项目维护者、同步服务开发者、数据库迁移评审者；不是外部 API 消费者。
覆盖数据集现有全部 canonical、provenance、execution、quality 与 publication 表。
市场语义不变；沿用现有 A 股、上海时区、交易日历、粒度、修订和 finality 决策。
数据迁移模型接入本身不搬数据、不改表名；仅 table/column COMMENT 需要 metadata-only revision。
完成定义32 张逻辑表全部建模，全部仓储切换，持久化目录无未批准 text()。

每个逻辑表只有一个定义位置。文件名与数据库表名完全一致；class 使用 PascalCase + Model，避免与领域对象同名冲突。

物理分区例外

年/月分区子表不是独立业务模型，不为每个日期分片复制 class。父表模型声明 partition key； 物理分区列表和创建策略进入专用 partition manager。

5. 模型声明规范

第一优先级是阅读，不使用会隐藏数据库行为的过度推断。以下示例只展示目标形态；实施时必须按 PostgreSQL pg_catalog 与历史 migration 逐项校准实际名称和默认值。 

class EquityInstrumentModel(Base):
    """标准证券身份锚点；行情和历史事实通过内部 `security_id` 关联。"""

    __tablename__ = "equity_instrument"
    __table_args__ = (
        CheckConstraint(
            "exchange IN ('SSE', 'SZSE', 'BSE')",
            name="ck_equity_instrument_exchange",
        ),
        Index(
            "ix_equity_instrument_exchange_symbol",
            "exchange",
            "symbol",
        ),
        {"comment": "保存证券稳定身份锚点及兼容 current projection。"},
    )

    security_id: Mapped[int] = mapped_column(
        BigInteger,
        primary_key=True,
        nullable=False,
        autoincrement=True,
        comment="数据库内部大表关联键，不对外暴露。",
    )
    instrument_id: Mapped[UUID] = mapped_column(
        PG_UUID(as_uuid=True),
        nullable=False,
        unique=True,
        comment="证券内部永久 UUID，不因名称或上市状态变化。",
    )
    exchange: Mapped[str] = mapped_column(
        String(4),
        nullable=False,
        comment="证券当前兼容投影所属交易所；历史解析以 identifier version 为准。",
    )
    symbol: Mapped[str] = mapped_column(
        String(6),
        nullable=False,
        comment="六位证券代码 current projection；不能单独作为永久身份。",
    )

强制规则

内容 规则 目的
Python 类型 全部字段使用 Mapped[T]；可空字段明确 T | None。 Pyright 能检查读取、赋值和 repository 映射。
数据库类型 全部显式写 BigInteger、Numeric(p,s)、JSONB、TSTZRANGE 等。 不要求阅读者记忆 SQLAlchemy 类型推断规则。
可空与默认 显式声明 nullable、server_default、Computed。 区分 Python 默认值与数据库权威默认值。
含义 class 中文 docstring、table comment、每个字段中文 comment。 代码和 PostgreSQL 工具都能显示业务语义。
约束 PK、FK、UNIQUE、CHECK、EXCLUDE 全部在模型文件内显式命名。 单文件内看到表的不变量和引用边界。
索引 普通、partial、covering、GIN/GiST 索引全部放 __table_args__。 索引不再只藏在 migration 历史中。
关系 FK 必须声明；默认不声明可写 relationship，不允许 lazy load。 避免 cascade、N+1 和循环 import 掩盖事务行为。
枚举状态 先保持现有 VARCHAR + CHECK，不顺手改为 PostgreSQL ENUM。 ORM 化不引入无关 schema 迁移或 enum 运维成本。
为什么不默认写 relationship() ORM class 与表结构映射完整，不要求每个 FK 都建立对象导航。当前同步仓储强调批量写、显式 join、 历史版本和严格事务；默认 relationship 会增加隐式查询与 cascade 风险。FK 已足够让表关系一目了然。 后续确有阅读或查询价值的关系，优先使用 viewonly=True 并配查询数测试。

6. 运行时与仓储全量迁移

6.1 Session 与事务

DatabaseClient 增加同步 sessionmaker。每个 repository 公开方法维持现有事务边界， 用显式 with session_factory.begin() as session 开始、提交或回滚。关闭 Session 后再返回领域对象， 禁止向 application 返回 attached ORM instance。 

application use case
  │  调用 provider-neutral repository port
  ▼
repository method
  │  session_factory.begin()
  ├─ SELECT / row lock / advisory lock
  ├─ raw provenance + canonical revision + quality + publication
  ├─ 成功：一次 commit
  └─ 任一步失败：一次 rollback，转换为现有领域错误
  ▼
domain result（不携带 Session / ORM state）

6.2 不把批处理退化为逐行对象操作

简单身份与读取

使用 session.get()、select(Model)、session.scalars()、 显式 join 和 ORM entity。适合目录、详情、当前 publication 等低行数路径。

行情、成员和质量批次

使用 Session.execute(insert(Model), list[dict])、批量 UPDATE/DELETE 与 RETURNING。 不为成千上万行创建完整对象图，不依赖 flush 顺序猜测。

6.3 PostgreSQL 特性映射

当前能力 ORM/SQLAlchemy 表达 实施限制
partial unique/index Index(..., unique=True, postgresql_where=...) 必须核对 predicate SQL 与现库一致。
covering index Index(..., postgresql_include=[...]) 覆盖列顺序进入 schema parity 测试。
双时间排斥约束 ExcludeConstraint + TSTZRANGE Alembic 自动检测不足，显式 migration。
生成范围列 Computed("tstzrange(...)", persisted=True) 表达式文本必须与 PostgreSQL 反射归一化核对。
JSONB checkpoint/证据 JSONB repository 边界继续验证中立 schema。
父分区表 postgresql_partition_by="RANGE (...)" 物理 child partition 由 migration/partition manager 管理。
upsert postgresql.insert(Model).on_conflict_do_update() onupdate 不会自动应用，SET 字段必须显式列出。
RETURNING insert/update(...).returning(...) 依赖输入顺序时必须显式排序或使用稳定业务键关联。
行锁 select(...).with_for_update() 保持现有锁顺序，避免新增死锁。
advisory xact lock select(func.pg_advisory_xact_lock(...)) 锁键算法必须与现有 hashtextextended 完全一致。

6.4 关键执行与失败路径

场景 目标行为 验证
正常同步 同一 Session 事务保存 source batch、canonical revision、质量结果与 publication。 集成测试断言所有 ID、版本和最终 current row 与旧实现一致。
重复运行 保留独立 source observation；相同业务内容不新增 revision/dataVersion。 同一分区连续执行两次，比较行数与 current publication。
provider/schema 失败 发生在 repository 前；ORM 化不得改变 raw、quarantine 或拒绝边界。 复用现有失败注入测试。
数据库失败 Session rollback 整个现有事务；不留下半个 publication。 在 provenance、canonical、quality、publish 各阶段注入异常。
进程中断/lease 过期 checkpoint、lease 与 reaper 语义不变。 membership/EOD 恢复集成测试。
物理分区缺失 专用 partition manager 建立目标月分区后写入；DDL 不混入 ORM model lifecycle。 跨月、并发建分区、权限不足和重试测试。

7. Alembic、Schema 权威与漂移控制

7.1 权威关系

Declarative models
  ├─ 人类阅读：当前目标 schema、字段含义、约束、索引
  ├─ Alembic target_metadata：生成候选 migration
  └─ Schema parity tests：与真实 PostgreSQL head 对比

Historical Alembic revisions
  └─ 数据库演进事实：从任意已支持版本升级到当前 head

禁止 Base.metadata.create_all() 管理生产数据库

“模型是当前目标 schema”“migration 是演进历史”并不冲突。已有 migration 必须保持不可变；未来 schema 修改先改模型，再生成候选 revision，人工补齐 PostgreSQL 特性后执行。模型不能代替升级步骤，migration 也不再是维护者理解当前完整 schema 的唯一入口。

7.2 首次对齐

  1. 冻结基线：以 0015 已验证实现和 migration 202607270004_sector_eod_snapshot 为当前 head 的一部分，从空 PostgreSQL 执行 alembic upgrade head，导出表、列、默认值、约束、索引、extension 和 partition 清单。
  2. 建立 32 个模型：按实际 catalog 名称声明，不重命名表、字段或既有约束。
  3. 接入 metadata：migrations/env.py 从显式 registry 加载 Base.metadata；限制只比较服务拥有的 public 业务表。
  4. 归零差异：alembic check 不得生成意外 table/column/index/FK 变更。 CHECK、EXCLUDE、partition 和 extension 另用 pg_catalog parity 测试。
  5. 注释迁移：单独 revision 添加 table/column COMMENT；不修改业务行、字段类型或约束。

7.3 Autogenerate 不能替代评审

可作为基础门

表/列增删、nullable、基础索引、显式 unique、基础 FK 和主要类型变化。

必须人工修正

表/列重命名会被看成 drop/add；server default 比较可能产生误报；复杂 PostgreSQL 表达式需要核对。

必须另建 parity 测试

CHECK、EXCLUDE、extension、物理 partition、运行时 DDL 与依赖数据库版本的特性。

8. 方案取舍

方案 可读性 实施成本 长期一致性 结论
文档/ER 图 + 现有 SQL 中；需要在代码和文档间切换 低 低；容易漂移 不采用：已被明确判定为过度复杂且非直接模型。
SQLAlchemy Core Table metadata 高 中 中高 不采用：仍保留字符串仓储和 Connection-only 事务。

9. 风险、隐患与控制

风险 暴露条件与影响 控制 退出条件
模型与现库漂移 类型、默认值、约束或索引写错，未来 migration 可能误删/重建对象。 空库升级、Alembic check、pg_catalog parity、禁止未审查 autogenerate。 32 表全部零意外差异。
表达式索引自动比较盲区 2026-07-28 实测 ix_equity_name_current_prefix 使用 lower(name) text_pattern_ops，Alembic 无法比较操作符类，只会假定索引相等。 保留模型声明；在 Session 仓储切换前补充针对该索引定义的 pg_catalog 断言和人工 migration 审查。 断言覆盖表达式、操作符类和部分索引条件后，才能将其纳入自动漂移门。
ORM 隐式行为 autoflush、lazy load、cascade 造成额外查询、写入或锁顺序变化。 禁 lazy、禁默认 cascade、显式事务与 join；关键路径查询数测试。 集成行为与 SQL 数预算通过。
批量写性能下降 日线、成分、EOD 把批量 SQL 改成逐行对象 flush。 强制 ORM bulk DML；记录批次 SQL 数、吞吐、内存和事务时间基线。 相同 fixture 不低于旧实现验收阈值；阈值先由基线确定。
锁/并发语义改变 identity、membership、EOD 的行锁或 advisory lock 顺序变化，引发竞争或重复发布。 逐条迁移锁语句；并发集成测试；保持锁键算法和锁顺序。 重复、并发、超时与 reaper 测试通过。

11. 已确认的决策

编号 建议 接受理由 不接受的影响
D1 接受：32 张逻辑表全部 Declarative 建模，最终仓储全量 Session 化。 直接满足“看得懂最高优先级”。 若只建模型不迁仓储，会长期保留模型与字符串 SQL 双轨。
D2 接受：一张逻辑表一个文件，并按业务能力分目录。 文件名即表名；单表字段、约束和索引集中。 多个表共文件会重新形成大型 schema 文件，不利于导航和代码归属。
D3 接受：物理日期分区不建立独立 ORM class。 分区是同一逻辑表的存储切片，不是产品实体；复制 class 会制造伪模型。 若要求每个物理分区一文件，未来每月都需新增代码，且字段重复必然漂移。
D4 接受：字段类型与 nullable 全部显式书写，不依赖类型推断简写。 牺牲少量代码长度，换取直接可读性。 模型更短，但维护者需要掌握 SQLAlchemy 推断规则才能确认数据库类型。
D5 接受：默认无可写 relationship/lazy loading，FK 与显式 join 为主。 避免隐式查询、cascade 和历史实体对象图；表关系仍由 FK 清楚表达。 若全面 relationship 化，需要额外查询数、cascade 和并发行为评审。
D6 接受：历史 migration 不改写，Declarative metadata 表达当前目标 schema。 既能一处看当前模型，也保留升级路径和已部署数据库兼容。 重写 migration 会破坏已有环境升级链，风险远高于收益。
D7 接受：模型 table/column comment 同步写入 PostgreSQL。 代码和数据库工具都能直接显示中文业务含义。 若只保留 Python docstring，psql/DBeaver 等工具仍看不到字段语义。
