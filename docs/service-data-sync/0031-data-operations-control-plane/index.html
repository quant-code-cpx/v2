数据运维控制面

在不改变 provider-neutral adapter 与 canonical 发布边界的前提下，以 service-data-sync PostgreSQL 建立数据集目录、全局串行队列、运行账本、健康评估、 动态计划和运维事件权威；Celery 只负责唤醒投递。所有 CLI、自动计划和内部 API 最终进入同一 dispatcher， 保证整个同步服务任一时刻最多一个同步运行。

1. 摘要

问题

数据存在，运维真相分散

当前有 138 张登记逻辑表、17 个具体 adapter、25 个 console script 和 17 个 Celery task， 但运行、checkpoint、质量、publication 与计划按领域分散。无法可靠回答“有哪些数据、最近是否成功、 为什么失败、谁触发了什么”。

决策

PostgreSQL 权威控制面

新增显式数据集注册表、command/run/attempt、全局租约与 fencing、schedule、health 和 append-only operational event。Redis/Celery 不保存权威状态，不承担锁和排序。

主要风险

旧入口绕过 fencing

只给新任务加锁不能满足全局串行。启用主动操作前，全部 legacy CLI/Celery、publication 和 checkpoint 写入必须进入统一 dispatcher，并在同一数据库事务校验当前 fence token。

选择理由 现有 canonical 数据与 adapter 无需搬迁；PostgreSQL 已是运行、来源和发布账本所在地，能用事务、行锁、 条件唯一索引和单调 token 同时解决幂等、队列、跨 worker 互斥和恢复。Celery 继续提供可靠投递， 但消息重复、worker 扩容或 scheduler 重启都不能改变数据库权威结果。
事实边界 本文盘点的是仓库在 2026-07-29 的 schema、adapter 与入口能力，不代表任一部署已经有对应数据行。 默认配置关闭所有外部来源；实际记录数、数据覆盖、最近成功和当前开关必须由运行环境数据库读取。 0002—0010 的 AKShare 调研和本文中的来源识别均不等于生产批准。

跨服务总览见 架构方案 0002； 机器可读边界见 内部 OpenAPI 0022。

2. 目标、非目标与任务契约

目标

  • 展示数据集、canonical 表、来源供应商、真实上游、方法学与可执行状态。
  • 分别展示最近尝试起止、最近严格成功、最近 publication、数据截至日、服务端 freshness、 观测状态与失败诊断。
  • 支持单个或批量的 FULL、INCREMENTAL、DATE_RANGE； 当前快照数据另用 OBSERVATION_DATE，不伪装成历史范围。
  • 人工与自动计划分别声明支持模式；v1 自动计划禁止 DATE_RANGE。
  • 手工、自动、重试和恢复共享一个全局串行队列。
  • 支持版本化健康检查、动态计划、取消、重试和完整审计回执。

非目标

  • 不让 service-api 或 service-web 直连同步数据库、Redis、S3 或数据供应商。
  • 不在本方案批准 Tushare、AKShare 或任一上游成为生产来源。
  • 不统一不同供应商的派生指标口径，不设计静默 fallback。
  • 不把 Celery result backend、消息队列顺序或 Redis 锁变成业务真相。
  • 不恢复成功批次原始载荷长期归档；继续遵守失败才留证。

硬约束

  • 全服务同时最多一条同步 run 处于有效执行态（RUNNING 或 CANCEL_REQUESTED）。
  • 所有 canonical publication/checkpoint 必须验证当前 fence token。
  • 时间使用 IANA 时区；A 股日频默认 Asia/Shanghai 和权威交易日历。
  • adapter 不写 canonical DB；应用层不导入供应商 SDK。
  • 首版 ADMIN、SUPER_ADMIN 可读；所有主动动作仅 SUPER_ADMIN。

任务定义卡

业务目的 / 消费者 让管理员经 service-web → service-api 查看并操作数据；service-api 只做身份、公开授权、可靠提交与公开审计。 写入本地 submission 后固定先返回 PENDING，不能把同步调用结果伪装成初始响应。
数据能力 覆盖当前已运行、影子研究和仅建模数据域；每项能力由注册表声明来源、粒度、模式、范围和 publication 语义。
市场与时间 A 股、ETF、指数、两融、港通、公司/交易事件和衍生品；具体市场、时区、交易日历、粒度与 finality 按数据集声明，禁止全局猜测。
历史与修订 FULL 是“来源已验证可提供的完整范围”，可能是全历史，也可能只是当前完整快照；增量含数据集定义的修订重叠窗。
容量假设 合同上限 首版批量最多 100 个数据集；日期范围的保守平台上限暂定 3660 天，每数据集可声明更小 maxRangeDays，最终值需压测校准。
来源权利 研究、内部、可再分发状态单独留痕；只有带可验证权利证据且能力门禁通过的来源可进入自动 production schedule。

3. 现状精确盘点

事实

持久化面

models/registry.py 当前显式登记 138 张逻辑表。存在共享 sync_run/sync_partition，但只被资金流、板块成分、板块 EOD、 财务派生及部分 source-batch 兼容路径使用，不能代表所有同步运行。

事实

执行面

25 个 console script 中 21 个属于同步或恢复操作；17 个 Celery task 分散注册。 worker 未固定并发为 1，也没有跨进程、跨数据集全局锁。CLI 可直接调用应用服务，绕过队列与统一账本。

事实

调度与观测

Celery beat 最多生成 9 个静态条目：个股 6 项、申万 1 项、板块 EOD dispatch 与 reaper 2 项。 时间写死在代码，只有布尔开关；无动态 schedule CRUD、统一健康度、操作者身份或监控平台。

3.3 当前 CLI、Celery、计划、checkpoint、质量与 publication 缺口

能力 已有事实 控制面缺口
CLI 个股、板块、财务、资金流、指数、ETF、两融、港通、事件、衍生品均有领域 CLI；部分支持日期范围或 full-history。 输入模型不统一；没有 commandId、actor、批量事务、统一状态；可直接执行并绕过队列。
Celery 17 个具名 task；acks_late、worker lost 重投；来源瞬时错误在部分任务指数退避。 任务可并行；没有全局 guard；不同领域 retry、timeout、queue、运行记录不一致；task event/result backend 均关闭。
schedule 上海时区静态 beat：个股 6 项、申万 18:30、板块 EOD 16:20，另有 5 分钟 reaper。 只能改代码/环境开关；无版本、动态频率、下一次触发、misfire、操作者与变更历史。
run / lease sync_run/sync_partition 已有 queued/running/succeeded/partial/failed/cancelled；板块 EOD 有 lease token。 sync_run 无 requested_by、请求参数、统一错误；只有部分链路写入。EOD token 只保护自身分区，不是全局 fencing。
checkpoint / recovery 通用、个股、生命周期、财务、申万、EOD 等多类 checkpoint；部分支持 replay/reaper/rollback。 语义和入口分散；成功载荷零归档后，不能假设所有 checkpoint 都可 raw replay；恢复能力未向统一目录声明。
quality / health 共享 quality 表及 financial、money-flow、sector-membership/EOD、SW 专用质量表；adapter 有 schema、单位和范围校验。 无统一健康 policy/evaluation；无法汇总 freshness、缺口、错误、UNKNOWN 原因，也没有主动评估入口。
publication dataset_publication、dataset_release 和领域 publication 并存；版本与质量可追溯。 所有 publication 路径没有统一 fence 检查；最新同步时间、最新成功和数据截至日不能由一个字段正确回答。
audit / observability 结构化日志有部分 run/batch/partition/provider 关联；diagnostics 检查 PostgreSQL、Redis、S3。 无操作者审计表、command 回执、统一失败分类、业务指标与告警；仓库未选择监控后端。

目录与来源

Dataset Registry

职责：登记数据集、capability、表、模式、粒度、日历、来源、方法学、权利与运行资格。

输入 / 输出：版本化代码 manifest 与迁移；输出可分页 catalog 和模式约束。

状态：对外 lifecycle 为 RESEARCH/CANDIDATE/PRODUCTION/RETIRED， availability 为 ENABLED/DISABLED/SOURCE_UNAVAILABLE/UNKNOWN；内部另保留 MODEL_ONLY，来源 approval 独立。

失败边界：manifest/DB 漂移时拒绝新命令，不影响既有消费者 publication。

命令与队列

Command Gateway + Dispatcher

职责：幂等接收单/批命令，校验权限和模式，展开有序 child runs， 提供 parent 聚合详情，并按 DB 顺序串行领取。

输入 / 输出：Idempotency-Key、submissionId、preflightId/requestHash、actorContext； data-sync 分配 commandId，输出新命令首个 child 的 queuePosition、有序 child runId 和 outcome。

状态：command、item、run、attempt、partition、global lease。

失败边界：Celery 重复或丢失只影响唤醒延迟，不改变 DB 中的队列和终态。

执行适配

Unified Run Executor

职责：把注册表中的中立请求翻译到既有应用服务，不把 provider 参数放进控制面。

输入 / 输出：归一 run spec + fence；输出 publication/checkpoint/失败分类。

状态：只通过 repository 修改 canonical；自身仅写阶段和 attempt。

失败边界：adapter、质量或持久化失败局限于当前 run；旧 publication 保持可读。

动态计划

Schedule Coordinator

职责：从 PostgreSQL 计算到期触发，以确定性幂等键生成 command，并唤醒 dispatcher。

输入 / 输出：TRADING_DAY/DAILY/WEEKLY/MONTHLY/INTERVAL、IANA 时区、 dataset spec、人工/计划模式矩阵、scheduleTargetPolicyOptions、targetPolicy、expectedVersion；输出 schedule fire。

状态：next/last fire、version、enabled、misfire。

失败边界：多实例用 DB 行锁协调；重启不会重复创建同一计划时刻的 run。

质量与健康

Health Evaluator

职责：对冻结 publication 执行 freshness、完整性、正确性、连续性和血缘检查。

输入 / 输出：policyVersion + dataVersion；规则范围由该 policyVersion 冻结，输出状态、0—100 score、不可变规则结果，以及带 issueProjectionAsOf 的当前开放问题安全投影。

状态：evaluation、issue、脱敏聚合 sampleSummary 和证据引用。

失败边界：未知日历/方法学得到 UNKNOWN；post-publication CRITICAL 不撤销既有 publication。

审计与诊断

Operational Event Ledger

职责：追加记录命令、权限判断、运行转移、计划变更、健康操作和结果。

输入 / 输出：actorRef/requestId/commandId/runId；输出稳定事件序列和脱敏诊断。

状态：append-only event；失败证据仅保存私有引用。

失败边界：事件与状态变更同事务；日志/指标后端失败不丢业务审计。

服务边界 service-api 不设置同步锁、不计算 queuePosition、不维护 run 终态。它保存“谁可靠提交了什么”的公开证据； 本地提交事务成功后一律先返回 PENDING，不能同步调用 data-sync 后改写初始响应。 service-data-sync 保存“命令如何执行并得到什么结果”的权威事实。两侧以 actorRef、requestId、submissionId、commandId 关联；系统命令没有 API submission， submissionId=null，仅通过固定 SYSTEM actorRef、commandId 和事件追溯， 任何一侧都不直连另一侧数据库。

5.2 数据观测与时间口径

DatasetObservationState 权威含义 不得混淆
PRESENT 已有可识别的观测数据，通常最新 publication rowCount > 0。 不代表 freshness 或 health 一定正常。
EMPTY_VALID 数据集 policy 明确允许该 scope 为空，且成功结果带稳定原因码。 不是来源失败，也不是“没有跑过”。
EMPTY_UNEXPECTED 预期应有数据却得到空集，或合法空证据不足。 不能显示为成功空数据；应关联 quality/error。
NOT_YET_SYNCED 从未形成该数据集的受理运行或 publication。 不能根据表存在显示“已有数据”。
UNKNOWN legacy 回填或证据不足，暂时无法判定。 不能等价为 EMPTY_VALID、失败或健康。
  • availability、observationState、last run 与 health 是四条独立轴；来源不可用、异常空集、失败、UNKNOWN 不合并为“无数据”。
  • lastAttemptStartedAt 取最近尝试 startedAt；lastAttemptFinishedAt 仅在终态存在，QUEUED/RUNNING 时为 null。
  • lastSuccessAt 只取最近 SUCCEEDED 的 finishedAt；PARTIAL 即使发布了部分分区也不计作“最近成功”。
  • freshnessStatus 为 FRESH/WARNING/STALE/UNKNOWN/NOT_APPLICABLE，并返回 lag value、 MINUTES/CALENDAR_DAYS/TRADING_DAYS/REPORTING_PERIODS 或 null 的 lag unit、稳定 freshnessReasonCode 与 freshnessEvaluatedAt； 全部由 data-sync 按版本化 policy 计算，Web 只展示。
  • 仅内部 implementationStage=MODEL_ONLY 的数据集允许 DatasetDetail.freshnessPolicy=null， 且 DatasetTiming.freshnessStatus 必须为 NOT_APPLICABLE；合同 oneOf 机器保证 freshnessPolicy=null ⇔ freshnessStatus=NOT_APPLICABLE，禁止半匹配组合。 Web 显示“不适用”，不能当作 UNKNOWN、STALE 或缺失配置。其他数据集缺 freshness policy 属于注册表漂移并阻断命令。

  • 管理员 retry 创建新 command/run 并关联原失败 run，保留完整事故历史。
  • 队列取消原子变为 CANCELLED；运行取消是协作式，不强杀阻塞中的 SDK 线程。
  • 若 publication 已提交，取消不能倒退数据版本；返回 cancel_too_late 事件 result=FAILED，并携带 ErrorSummary(stage=CANCEL, code=cancel_too_late)；目标 run 保留真实 SUCCEEDED。 取消动作只有在目标进入 CANCELLED 时才算达成，CANCEL_REQUESTED 只表示已受理。

权威 schema 归属 0022 OpenAPI。 v1 共 18 个内部 POST，固定前缀 /internal/v1/data-operations，所有请求继续使用服务 Bearer； service-api 注入受信 actorContext，浏览器字段不能直接成为 actor。

  • actor = { actorRef, role, reason }；首版写操作只接受 SUPER_ADMIN，跨服务请求 ID 使用 X-Request-Id。
  • 浏览器公开 Idempotency-Key 由 service-api 按 actorId 分域保存，不能原样转发； service-api 以 submissionId 确定性派生并稳定复用独立的内部 Idempotency-Key。
  • data-sync 按 caller_service + idempotency_key_hash 去重，首次受理后返回 commandId；未知内部提交结果只能复用原内部 key。
  • submit 带未过期 preflightId 与规范化 JSON 的 requestHash；未知结果不得换 key 重试。
  • 同步项含 datasetCode、mode、严格业务 selector、可选 dateFrom/dateTo 或 observationDate。selector 只能是 capability 声明允许的 GLOBAL、INSTRUMENT、SECTOR、SCHEME、EXCHANGE、CONTRACT、ETF、MARGIN、 STOCK_CONNECT、TRADING_EVENT 或 INDEX 判别结构；它不接受 Provider 参数、URI 或凭据，并在 Run 受理时冻结。v1 同一 preflight/submit 请求内 datasetCode 必须唯一，重复目标返回 422。
  • cancel/retry 必须带 target={resourceType: COMMAND|RUN, resourceId}： COMMAND 作用整批，RUN 只作用单个 child，禁止由服务端猜测作用域。
  • data-sync 内部 receipt 含 完整 CommandStatus、target、targetStatus、1—100 个 childRunIds、queuePosition 和 acceptedAt； target=COMMAND 时 targetStatus 是命令状态，target=RUN 时是子运行状态，不能用 command status 代替。submit/retry 的 queuePosition 只表示新命令首个 child run 在受理事务快照中的位置；cancel 固定为 null，其余 child 位置从 CommandDetail.childRuns 读取。 公开初始响应仍固定 PENDING 且 queuePosition=null， 后续才对账 ACCEPTED/REJECTED/DEAD_LETTER。

详情体积边界

  • RunDetailRequest 除 runId 外可带 partitionsCursor/partitionsLimit 与 timelineCursor/timelineLimit；两组 limit 默认 100、最大 200，可独立或同时续页。
  • RunDetail 必返 partitionCount、partitions、partitionsNextCursor、 timelineEventCount、timeline、timelineNextCursor；partitions 与 timeline 每页各最多 200 项，刷新其中一组不得改变另一组游标。
  • 内部 RunDetail.partition.checkpoint 只能是 null 或 CheckpointSummary={kind, positionHash, updatedAt}；positionHash 为 SHA-256， kind 最长 40 字符。不得返回 raw checkpoint、Provider cursor、token 或 payload； 公开 0023 RunDetail partition 不含 checkpoint 字段。
  • DatasetSummary.sourceBindings 最多 10 项，DatasetDetail.healthRules 最多 200 项， 每个 preflight target 的 warnings 最多 20 项；HealthEvaluation detail 的 results 最多 500 项，search 不返回 results。
  • HealthDetailRequest 可带 issuesCursor/issuesLimit，limit 默认且最大均为 100； HealthDetail 必返 evaluation、currentOpenIssueCount、currentOpenIssues、 currentOpenIssuesNextCursor、issueProjectionAsOf。currentOpenIssues 每页最多 100 项， 只含 OPEN/ACKNOWLEDGED 的脱敏安全摘要；问题续页不改变仍最多 500 项的 immutable rule results。 首次查询在同一读取快照计算 count/list/asOf，后续 opaque cursor 固定该 issueProjectionAsOf， 防止 ACK/RESOLVE 并发导致翻页重排。
  • HealthCheckDetail 以 1—100 个原提交 targets 的 sequence_no 排序，逐项返回 resolvedDataVersion、status、evaluationId、error。SUCCEEDED 必有 resolvedDataVersion + evaluationId 且 error=null；FAILED 必须 evaluationId=null 且有 error；REJECTED 还要求 resolvedDataVersion=null。RUNNING 必有 resolvedDataVersion 且 evaluationId/error 为 null； QUEUED 与 CANCELLED 的 evaluationId/error 也必须为 null，resolvedDataVersion 只在已经成功绑定目标版本后有值。API reconciler 可按 healthCheckId 轮询到批次终态；主动检查产生的 HealthEvaluation.healthCheckId 反向关联该批次，自动发布后评估则为 null。v1 同一批次 datasetCode 必须唯一，重复目标在创建批次前返回 422。
  • 上述边界和游标必须在 repository 查询层生效，禁止先把全部明细载入内存再截断， 以降低触发跨服务 2 MiB 响应体限制的风险，并避免大 run 拖垮控制面。

6. 全局串行、模式、批量、恢复与计划

6.1 全局 singleton lease 与 fencing

  1. dispatcher 仅从 PostgreSQL 按受信 queue_priority + queue_sequence 选择首个可运行的 QUEUED run；首版所有业务命令固定同一优先级，实际行为为 FIFO，用户不能提交 priority。
  2. 事务锁定 sync_global_lease(global-sync)；无有效持有者时，将 token 单调加一，同时把 run 置为 RUNNING 并创建 attempt。
  3. OperationsOverview.executionSlot 严格执行合同 oneOf：IDLE 时 runId/datasetCode/leaseUntil/heartbeatAt 全为 null；RUNNING 或 RECOVERING 时四者全为非空。repository 在同一读取快照联结 active run， 禁止返回半空槽状态。
  4. worker 每 15 秒 heartbeat，默认 60 秒 lease；具体值由环境配置和故障注入校准，不由 UI 改动。
  5. 每个 canonical publication、checkpoint、release、可见 availability 以及 run/attempt 终态写入事务， 先锁定 guard 行并校验 run、token 和未过期 lease。
  6. lease 过期时 reaper 在锁内把槽标为 RECOVERING，将 attempt 置 INTERRUPTED，再让 run 回到 QUEUED 或 FAILED；新 attempt 获得更大 token。旧 worker 即使恢复也因 token 失效无法提交。
  7. 数据库增加“最多一条 RUNNING/CANCEL_REQUESTED”的条件唯一约束，作为 lease 逻辑之外的第二道防线。
不可省略的实现范围 worker --concurrency=1 只能作为防御性配置，不能代替数据库 guard；单机进程锁、Redis 锁和 Celery queue concurrency 都无法覆盖多个 worker、副本、CLI 和 scheduler。任何旧 publication 仓储未接入 assert_current_fence() 时，主动同步功能必须保持关闭。

run 冻结受理时的来源与 policy 版本用于复现，但领取和首次 Provider fetch 前仍须重查 dataset 总开关、 当前 approval 与紧急 suspension。更严格的新状态立即以稳定错误终止旧队列项；不得静默换来源或改写原 spec。

6.2 FULL、INCREMENTAL、DATE_RANGE、OBSERVATION_DATE

模式 统一语义 数据集约束 幂等 / checkpoint
FULL 覆盖该来源已经验证的完整可获取范围。 full_scope 必须声明 ALL_AVAILABLE_HISTORY 或 CURRENT_COMPLETE_SNAPSHOT；不能把当前快照宣传为历史全量。 按稳定分区重建候选并比较内容；不变不创建新 revision/publication。
INCREMENTAL 从最后成功 publication checkpoint 开始，并重拉注册表声明的修订重叠窗。 没有可靠 watermark 时必须声明 bootstrap 策略；不得自行降级为 full。 只有 publication 成功后推进跨 run checkpoint；失败保留旧水位。
DATE_RANGE 同步包含端 start/end；按交易日历或来源粒度切分稳定分区。 当前快照 adapter、无历史参数的指数/目录/成分能力禁用；全局上限假设 3660 天，数据集可更小。 规范化 request key 包含 dataset、target、范围、模式、方法学版本。
OBSERVATION_DATE 对只提供当前横截面的来源记录一次具名观察日，不声称获得该日期的历史版本。 adapter 必须校验 observationDate 与来源实际可观察时点；只支持“今天”的来源拒绝过去或未来日期， 合法空集必须带原因。 request key 包含 dataset、observationDate、来源与方法学版本；重复观察内容不新建 publication。

日期缺失不能自动解释为休市；只有注册表绑定且已覆盖目标年份的权威日历才允许完整性判断。 对 listing、suspension、no-trade、公司行动和复权口径，继续使用各数据集既有语义，不在 dispatcher 中统一猜测。

6.3 批量与队列

  • 单 command 按 0022 合同最多 100 项；先验证全部 dataset/mode/target/range/权限，再一次事务写 command items 和 child runs。v1 同一请求内 datasetCode 必须唯一；preflight 与 submit 均在写入前拒绝重复项并返回 422，数据库 UNIQUE(command_id, dataset_key) 作为末级防线。
  • child run 按请求顺序获得连续 queue sequence，但每条 run 独立终态；父 command 聚合 SUCCEEDED/PARTIAL/FAILED。
  • 首版同优先级严格 FIFO，不给手工任务静默插队。自动重试若处于 backoff，后续已就绪 run 可执行。
  • CommandReceipt.queuePosition 是受理事务中的精确快照：submit/retry 只返回新命令首个 child 的位置，cancel 为 null；其余 child 位置读取 CommandDetail.childRuns。 任一位置都不承诺等待秒数；同时展示 oldestQueuedAt 和 active run 供运维判断。
  • 一个 run 内的 partitions 首版顺序执行，避免“只有一个 run 但内部并行几十个证券”违背产品预期和供应商限额。
  • RunSummary.progress 同时返回 completed/totalPartitions 与 processedRecords/estimatedRecords； Provider 不能可靠估算时 estimatedRecords=null，UI 不显示虚假百分比。

6.4 取消、重试、幂等与恢复

取消与 retry

  • target=RUN：只操作 resourceId 指定 child；QUEUED 原子变 CANCELLED，RUNNING 进入 CANCEL_REQUESTED，不得连带同 command 的其他 runs。
  • target=COMMAND 取消：未开始 child 原子变 CANCELLED；唯一活跃 child 进入 CANCEL_REQUESTED；既有终态不改写。
  • RUNNING：在 Provider 请求前后、分页/分区间、quality gate 和 publication 前检查取消。
  • SDK 阻塞调用只受既有 timeout 约束；不在线程中注入强制异常。
  • 若 CANCEL_REQUESTED 后 lease 过期，reaper 记录 INTERRUPTED attempt 后终结为 CANCELLED，不得重新排队。
  • target=COMMAND 重试只复制可重试的 FAILED、PARTIAL、INTERRUPTED child； target=RUN 只复制指定且可重试的 child。两者均重新 preflight，创建新 command/run 并记录 retry_of。

崩溃与恢复

  • Celery 重投只唤醒 DB dispatcher；重复消息不创建重复 run。
  • 成功分区与 publication 保持，恢复只处理未成功分区。
  • 成功 payload 按 ADR-0021 不保留，恢复不得假设 raw replay 可用。
  • 失败 evidence 可在保留期内重放；否则重新抓取或明确标记不可恢复。

6.5 动态 schedule

  • 只支持结构化 TRADING_DAY、DAILY、WEEKLY、 MONTHLY、INTERVAL；字段为 localTime/dayOfWeek/dayOfMonth/intervalMinutes、 IANA timezone 和可选 calendarCode，禁止用户输入任意调度表达式。
  • TRADING_DAY 必须有 calendarCode/localTime；DAILY 必须有 localTime；WEEKLY/MONTHLY 再分别要求 1—7 的 dayOfWeek / 1—31 的 dayOfMonth；INTERVAL 仅接受 5—43200 分钟且 localTime/dayOfWeek/dayOfMonth/calendarCode 全为 null。其余 kind 的无关 day/interval 字段也必须为 null， 服务端按 IANA timezone 计算未来五次触发。
  • 自动计划只接受数据集 scheduleSupportedModes 中的 FULL、INCREMENTAL、OBSERVATION_DATE； 它与人工 supportedModes 独立，首版禁止自动 DATE_RANGE。
  • 数据集同时返回 scheduleTargetPolicyOptions。每个支持的计划模式至少有一个 {mode, policy, isDefault} 允许项且恰有一个默认项，重复项或没有/多个默认项 均阻断 manifest seed。默认值只供 Web 预选，不表示服务端可省略 targetPolicy。 schedule upsert 必须逐字段匹配所选数据集和 mode 的一个当前允许项，data-sync 真正受理时再次校验， 不能只信任 Web 或 service-api 的旧目录快照。
  • targetPolicy.policyVersion 必须 ≥ 1，并随 schedule revision、fire 和生成的 run spec 冻结。 FULL/INCREMENTAL 必须使用 dateResolution=NONE；OBSERVATION_DATE 必须选择 SCHEDULED_LOCAL_DATE 或 LATEST_COMPLETED_TRADING_DATE。
  • SCHEDULED_LOCAL_DATE 取 scheduledFor 转换到计划 timezone 后的本地日期； LATEST_COMPLETED_TRADING_DATE 按触发时刻和注册表绑定的权威 calendarCode 解析最近已完成交易日。 缺日历、日历未覆盖或无法证明“已完成”时，fire 以稳定原因拒绝/跳过，不能猜测成自然日。 解析后的 observationDate 写入 fire、command item、normalized run spec 和幂等请求摘要。
  • 固定 scheduler tick 轮询 PostgreSQL 并解析到期计划，使用 FOR UPDATE SKIP LOCKED； Celery 只接收 dispatcher wake-up，计划表达式不是 Celery beat 配置。
  • 计划触发 Idempotency-Key = UUIDv5(scheduleId, scheduledFor, scheduleVersion)，重复 tick 复用同一 command receipt。
  • misfirePolicy 只允许 SKIP 或 RUN_ONCE；coalesce=true 时合并漏跑并记录 coalesced fire，避免恢复风暴。
  • schedule create 要求 scheduleId/expectedVersion 同为 null；update 要求两者同为非 null， expectedVersion 必须等于当前版本。半空组合返回 422，不能借 create 语义覆盖现有计划或绕过乐观锁。 set-enabled 也必须携带匹配当前版本的 expectedVersion。成功 upsert 与启停都生成不可变 revision， 写 before/after hash 与 actorRef；首版以禁用代替删除。
  • v1 以 datasetCode 为计划唯一键，数据库 UNIQUE(dataset_key) 覆盖启用和禁用计划。 同数据集重复 create 返回 409；update 必须保持原 datasetCode，禁止把既有 scheduleId 改绑到另一数据集。计划还冻结一个 capability.selectorKinds 允许的严格 selector，scheduler 仅把该 selector 连同解析日期转换为 command； 需要替换时只能更新同一记录及其 revision。
  • 迁移时按现有静态时间建立禁用计划；核对 nextRunAt 和未来五次触发后再关闭旧 beat、启用新 coordinator，不能双投。

7. 数据健康、质量门与派生方法学

7.1 健康维度

数据集 availability（ENABLED/DISABLED/SOURCE_UNAVAILABLE/UNKNOWN）属于目录可用性，不和健康结论混成一个枚举。 0022 合同只导出下列八个 health dimension；可用性与合法空集作为规则证据和 UNKNOWN 原因展示。

维度 示例规则 证据与阈值 处置
FRESHNESS lastPublishedAt、dataAsOf 落后预期 cadence freshness policy + dataAsOfKind/Label + 时区/日历；不用抓取时间替代业务日期 超 warn/critical 阈值产生 issue
COMPLETENESS 缺交易日、缺证券、横截面覆盖不足、分页缺失 权威日历、上市生命周期、预期 universe/release；未知即 UNKNOWN blocking 规则阻止 publication；事后检查只告警
VALIDITY OHLC、金额/成交量单位、空值、范围、net 恒等 类型与业务不变量；只验证来源明确提供的恒等式 reject / quarantine / warn / publish
UNIQUENESS 业务键、source identity 或同 dataVersion 重复 canonical grain、唯一约束与去重证据 关键键重复为 CRITICAL
CONSISTENCY 父子闭包、发布行数漂移、checkpoint 超前、fence 不匹配 同事务 FK、release/publication/checkpoint 不变量 发布不一致为 CRITICAL；修复必须显式受审计
IDENTITY 证券代码映射、板块成员、来源与真实 upstream 缺失 有效证券集合、source registry 与 canonical lineage 身份不明隔离；无法判断时 UNKNOWN
SCHEMA fingerprint 漂移、字段/类型/单位或 adapter/methodology 改版 source batch、contract fingerprint、methodology version 不兼容 schema drift 默认 blocker
TEMPORAL 异常跳变、旧日被删除、revision/window 冲突、PIT 可见时间错误 同来源、同方法学、同 finality 历史；保留 content hash 异常样本与来源 batch 关联

健康评估绑定 dataVersion + policyVersion，规则范围由该 policyVersion 冻结。同步过程内的 pre-publication quality gate 在 RunDetail 的 qualityGate 中独立呈现 NOT_EVALUATED/PASSED/WARNED/BLOCKED； 只有 BLOCKED 能阻止当前候选 publication。控制面的 post-publication health 绑定既有不可变版本， 即使结果为 CRITICAL 也只标记该版本严重异常，不撤销、不阻断已经存在的 publication， 也不自动静默回滚。人工确认、重新同步或 publication rollback 都是独立受审计操作。

  • health/evaluations/search 只返回 HealthEvaluationSummary：身份、policy、聚合状态、score、 healthCheckId、warningCount、criticalCount、currentOpenIssueCount、affectedRecordCount、 evaluatedAt 和 issueProjectionAsOf，不包含 results。目录里的 HealthSummary 仍返回 openIssueCount，避免把仍待处理的问题藏在总体健康状态后。
  • HealthEvaluation 是不可变事实，主动检查生成时 healthCheckId 反向指向批次，自动评估时为 null。 HealthDetail 将该 evaluation 与查询时问题投影组合：按 issuesCursor/issuesLimit 返回最多 100 条 currentOpenIssues、currentOpenIssuesNextCursor、currentOpenIssueCount 和 issueProjectionAsOf。 currentOpenIssues 只含 OPEN/ACKNOWLEDGED，evidenceSummary 仅为脱敏聚合证据； immutable results 仍最多 500 项，列表页禁止预取规则或问题样例。
  • evaluation 与 summary 返回 0—100 的 score；UNKNOWN 且证据不足以评分时为 null，不能伪造 0 分或 100 分。
  • 每条规则分别返回 INFO/WARN/CRITICAL severity，以及 PASSED/WARNED/FAILED/UNKNOWN/SKIPPED 的规则 status、expected/observed、affectedCount 与 message；聚合状态不能替代规则明细。
  • sampleSummary 最长 500 字符，只允许脱敏、聚合后的安全摘要；不得返回原始行情、账号、凭据或可反推敏感记录的逐行样本。

7.2 派生市场数据比较准入

资金流和供应商估算不得做普通跨源对账 东财 order-size 与同花顺 trade-direction 属于不同语义族和方法学。健康规则只能分别检查各自范围、单位、 恒等、完整性和新鲜度；没有语义族、方法学版本、universe、窗口、截点、分桶、分母、单位和 finality 全部一致的证据，不得要求两者数值相等、拼接补洞或自动切换。
  • canonical 身份必须保留 adapter provider、真实 upstream、source dataset、semantic family、methodology ID/version/status。
  • 供应商报告值、盘中快照、EOD、滚动排行和平台日频派生值使用不同 dataset/指标身份。
  • 财务派生指标继续独立保存公式版本、输入 publication、覆盖率和计算时间，不覆盖来源报告值。
  • 切换主来源属于数据定义变更：另建/更新 ADR、双跑重叠窗口、量化偏差、标记断点并决定回补。
  • 来源权限或方法学未知时可完成研究采集，但 production schedule/publication 保持关闭。

7.3 健康状态

HEALTHY

所有适用 blocking/error 规则通过，warn 数为零；证据、日历和方法学完整。

WARN / CRITICAL

WARN 有非阻断缺口；CRITICAL 有 blocking error、publication 不一致、关键键重复或严重过期。

UNKNOWN

无 publication、日历/来源/方法学不明或检查不可执行。UNKNOWN 不是 HEALTHY，也不自动当作市场休市。

8.2 审计事件

至少记录以下事件，并与状态变更同事务：

  • 命令 received/accepted/rejected、批量展开、幂等重放、hash conflict；
  • run queued/claimed/heartbeat/lease-lost/requeued/cancel-requested/terminal；
  • source fetch、schema drift、quality disposition、publication/checkpoint 结果；
  • schedule create/update/enable/disable/delete/fire/coalesce；
  • health requested/completed、issue opened/acknowledged/resolved；
  • 权限拒绝、fence 拒绝和管理员 retry/cancel。

OperationEvent.result 固定为 ACCEPTED/QUEUED/STARTED/CANCEL_REQUESTED/SUCCEEDED/PARTIAL/ FAILED/CANCELLED/INTERRUPTED/SKIPPED/REJECTED，表达“这次动作”的结论，不冒充资源终态。 因此取消请求可先产生 CANCEL_REQUESTED；只有目标状态为 CANCELLED 才算取消达成。 cancel_too_late 必须记录 FAILED + stage=CANCEL + 稳定 code，目标仍可真实 SUCCEEDED。

actorRef 是稳定用户引用，roleAtRequest 是操作时角色快照；显示名称由 service-api 自己的用户边界解析。自动计划、迁移期 legacy、内部恢复命令的 submissionId 均为 null，actorRef 分别使用 system:schedule/{scheduleId}、system:legacy、 system:recovery，不得伪造具体用户。

运维事件保留期尚待治理批准：建议 365 天在线后受控归档；在归档、检索和 legal hold 流程落地前， 安全默认是不自动删除。用户删除后仍只保留不透明 actorRef，显示层回退为“已删除用户”。固定 SYSTEM actorRef 则分别显示“系统计划”、 “遗留任务”、“系统恢复”，不得使用该用户兜底。

8.3 失败分类与安全回执

下表 failure category 与 ErrorSummary.stage 正交；stage 固定为 PREFLIGHT/QUEUE/DELIVERY/PROVIDER_FETCH/NORMALIZE/QUALITY_GATE/HEALTH_EVALUATION/ PERSIST/PUBLISH/CHECKPOINT/SCHEDULE/CANCEL/RECOVERY。新增 DELIVERY 用于跨服务投递， HEALTH_EVALUATION 用于发布后规则执行，SCHEDULE 用于计划校验、解析或触发； 不得继续把三者笼统归入 QUEUE、QUALITY_GATE 或 INTERNAL。

8.4 日志、指标、追踪与告警

  • 所有日志关联 request_id、command_id、run_id、attempt、fence、dataset、partition、provider、upstream。
  • runId 等高基数字段只用于日志/trace，不作为指标 label。
  • 核心指标：queue depth/oldest age、active run、lease remaining/fence rejects、run outcome/duration、source error/latency、publication age、health status/issues、schedule lag/misfire。
  • 告警建议：active run > 1 立即 P0；oldest queue、lease 连续丢失、publication 过期、CRITICAL、schedule lag 按数据集 policy。

9.1 方案取舍

9.2 实施与迁移

  1. 阶段 A｜只读基线：增加 registration/source manifest、补齐腾讯与板块 batch 血缘、 新增 catalog/run/health 只读投影；用现表回填“已知/未知”，不推断实际数据存在。
  2. 阶段 B｜控制面账本：迁移 command/item/run-attempt/event/schedule/health/global-lease； 旧 sync_run 回填 LEGACY actor/trigger，缺失字段保持 unknown。
  3. 阶段 C｜Shadow 对账：旧 CLI/Celery/beat 在原路径执行，同时写不可领取的 SHADOW command/run/event；逐数据集核对来源、状态、时间和失败映射，禁止 shadow dispatcher 真正抓取或发布。
  4. 阶段 D｜统一执行：为所有 publication/checkpoint/终态增加 fence 校验；CLI/Celery 改为提交 command； architecture test 禁止 entrypoint/messaging 直接调用领域 sync service。
  5. 阶段 E｜计划切换：先关闭旧 beat 开关并等待 in-flight 完成；按原时间创建禁用 DB schedule， 对比 nextRunAt 与未来五次触发；再启用新 coordinator。不得同时运行两套计划。
  6. 阶段 F｜主动操作：双 worker 故障注入、幂等、安全与质量验收通过后， 才向 SUPER_ADMIN 开启 sync/health/schedule/cancel/retry。

9.3 Compose 与部署影响

  • 不新增基础设施：PostgreSQL 保存控制面；Redis 仍只作 Celery broker；MinIO/S3 仍只保存失败证据。
  • data-sync-api 增加内部 operations POST；仍只在内部网络监听并使用 Bearer。
  • data-sync-worker 接受 dispatcher wake-up；建议 concurrency=1，但数据库 guard 允许未来多副本安全竞争。
  • data-sync-scheduler 改为 PostgreSQL schedule coordinator；多实例用行锁/确定性 fire 去重。
  • data-sync-migrate 先执行 additive migration 和 manifest seed；生产 image 仍使用 immutable digest。
  • 凭据继续由环境/secret 注入；新增 lease/heartbeat/poll 参数进入 .env.example，schedule 业务值不放环境变量。

9.4 回滚

启用前

关闭 operations write feature 和 DB schedules，保留只读目录；schema/event 为 additive，无需删表。

fence 强制前

可在确认无 queued/running command 后重新启用旧静态 beat；必须避免两套 scheduler 并存。

fence 强制后

旧 binary 不携带 token，不能安全回滚。只允许 roll-forward 修复或关闭新写入；canonical 数据与旧 publication 不删除。

9.7 验收标准

  • 目录能逐项回答：数据集、业务表、是否真实有 publication、AKShare/Tushare 等访问供应商、进一步上游、方法学与来源资格。
  • 每项清楚区分 availability、observationState/reason、lastAttemptStartedAt/FinishedAt/status、 lastSuccessAt、lastPublishedAt、dataAsOf、dataAsOfKind/dataAsOfLabel、latestRun、latestError 和 health； lastSuccessAt 只认 SUCCEEDED，Web 不自行猜测业务日期、新鲜度或空集语义。合同 oneOf 验证 freshnessPolicy=null ⇔ freshnessStatus=NOT_APPLICABLE，仅 MODEL_ONLY 使用该组合。
  • 目录检索可同时按访问 Provider 与 upstreamSources 过滤，并保留 adapterId/sourceDataset/methodology/approval。
  • DatasetCapability 分别返回可为空的人工 supportedModes 与计划 scheduleSupportedModes； 单/批四种人工模式只在人工矩阵内可提交，计划仅允许 FULL/INCREMENTAL/OBSERVATION_DATE， v1 自动 DATE_RANGE 必须拒绝。 scheduleTargetPolicyOptions 覆盖每个计划模式且各有唯一默认项，upsert 只接受逐字段匹配的当前允许策略。
  • schedule frequency 严格执行 oneOf 字段条件；targetPolicy.policyVersion 随 revision/fire/run 冻结， FULL/INCREMENTAL 只用 NONE，OBSERVATION_DATE 按计划本地日期或最近已完成交易日解析并冻结目标日期。create 的 scheduleId/expectedVersion 同为 null，update 同为非 null 且版本匹配； 半空组合稳定返回 422。数据库保证每个 datasetCode 最多一个计划； 重复创建返回 409，更新不可改绑 datasetCode。
  • service-api 本地 submission/outbox/audit 事务成功后固定返回 202 delivery=PENDING、queuePosition=null； dispatcher 后续才对账 ACCEPTED/REJECTED/DEAD_LETTER，初始响应不受同步调用结果影响。接受后 submit/retry 的 queuePosition 只表示新命令首 child 的受理事务快照位置，cancel 为 null， 其余 child 从 CommandDetail 读取。
  • commands/detail 返回完整聚合状态与按提交顺序排列的 childRuns；只有创建 child 前 REJECTED 可返回空数组，其余至少一项。 CommandReceipt 必返完整 status、target/targetStatus；submit/retry 的新命令与 cancel 所属命令语义清楚，oneOf 强制 COMMAND targetStatus=CommandStatus、 RUN targetStatus=RunStatus，批次和单 child 作用域无歧义。
  • schedule/legacy/recovery 的 CommandDetail 均为 submissionId=null，并分别携带 system:schedule/{id}/system:legacy/system:recovery；API 显示系统计划/遗留任务/系统恢复， 不显示成已删除用户。
  • RunSummary 同时返回分区与 processed/estimated records 进度，无法估算时 estimatedRecords=null； RunDetail 必返受理时冻结的 sourceSnapshot，来源配置更新后历史 run 仍显示当时 Provider、真实上游、 adapter 和方法学版本。RunDetail 的 partition/timeline 分别使用默认 100、最大 200 的独立游标，并必返两组总数和 nextCursor。 内部 checkpoint 仅返回 CheckpointSummary，公开 0023 不返回 checkpoint； raw/provider cursor/token/payload 均不得外泄。
  • 手工、计划、retry、legacy 迁移入口并发触发时，数据库中最多一个有效执行态；过期 worker 不能写任何 publication/checkpoint。ExecutionSlot 通过 oneOf 保证 IDLE 的 runId/datasetCode/leaseUntil/heartbeatAt 全空， RUNNING/RECOVERING 时全非空，禁止半空状态。
  • v1 同步 preflight/submit 和主动健康检查的同一请求内 datasetCode 必须唯一；重复目标在创建 command、run 或 health check 前稳定返回 422， 不产生部分批次。
  • 同一内部 Idempotency-Key + requestHash 重复投递返回原 receipt 且不重复运行；同 key 异 payload 返回 409；schedule 重启不重复 fire。
  • 取消、自动恢复、人工 retry、provider timeout、schema drift、质量阻断和 DB 失败均有稳定状态、原因与审计事件。ErrorSummary.stage 覆盖 DELIVERY/HEALTH_EVALUATION/SCHEDULE；OperationEvent.result 覆盖 CANCEL_REQUESTED/INTERRUPTED/SKIPPED。取消仅在目标 CANCELLED 时达成； cancel_too_late 记录 FAILED + stage=CANCEL，目标可保持 SUCCEEDED。
  • RunDetail 的 qualityGate 独立显示 BLOCKED；健康检查能识别缺失、重复、错误、过期和血缘缺口， 返回 score/severity/affectedCount/脱敏安全摘要。post-publication CRITICAL 不撤销或阻断既有 publication； 未知日历/方法学返回 UNKNOWN。 HealthSummary 必返 openIssueCount；HealthEvaluationSummary 必返 currentOpenIssueCount + issueProjectionAsOf。HealthEvaluation 是不可变事实； HealthDetail 组合最多 500 条 results 与最多 100 条 OPEN/ACKNOWLEDGED currentOpenIssues，并返回 currentOpenIssuesNextCursor 和 issueProjectionAsOf。
  • health/checks/detail 返回按原 target 顺序排列的 1—100 个批次结果，API reconciler 可轮询到终态；SUCCEEDED 必有版本/evaluation 且无 error，FAILED/REJECTED 必有 error， queued/running/cancelled 组合通过 oneOf 校验。主动 HealthEvaluation.healthCheckId 反向关联批次，自动评估为 null；批次内 datasetCode 唯一。
  • 合同体积边界生效：sourceBindings≤10、healthRules≤200、每个 preflight target warnings≤20、currentOpenIssues 每页≤100；超限由 manifest/policy/preflight/query 阶段显式处理，不能在响应层静默丢失。
  • 公开 RunDetail.timeline 和 HealthCheckDetailView 不出现 actorRef，只返回 ActorDisplay/requestedBy；SYSTEM 映射固定标签，USER 删除后才使用“已删除用户”。
  • ADMIN/SUPER_ADMIN 读权限正确；所有主动动作只有 SUPER_ADMIN，data-sync 二次校验。
