结论

事实

8 项有业务字段候选

三表、快报、指标、预告、预约披露和主营构成均返回结构化数据；审计候选仅有财务公告标题和链接。

决策

Tushare 保持主路由

首轮没有任何 FULL。AKShare 仅保留 provider-neutral adapter 的调研证据，不创建真实 adapter 或 fallback。

最大风险

版本不等于更新时间

三表虽然带“更新日期”，但本样本每报告日只有一行；不能据此声称保留首次披露、修订版或可回测的 point-in-time 财务事实。

本轮决定：财务数据不得按“字段看起来相近”直接写入 canonical schema。报告期、公告日、首次公告日、报表类型、合并范围、累计/单季、币种/单位和更新版本必须全部有可验证来源后，才可讨论受限接入。

财务版本与口径：本批不可跳过

报告期不是可用时点

回测和信号生成需以公告日、首次公告日和实际可得版本为准。只有 end_date 的报表会把未来信息带入历史；“更新日期”也不自动代表当时可用版本。

累计与单季必须拆开

季报、半年报和年报常是累计值，单季值可能需要从相邻累计期推导。推导前要固定报表口径、缺报处理、合并范围和修订链，不能混入来源原始值。

合并/母公司和银行科目

三表候选含“类型”，但它是否完整表达合并、母公司、期末/期间与报告类型尚未证实。金融业特有科目在不同来源的命名、单位和空值含义也须逐项映射。

公告计划是状态快照

首次预约、多次变更和实际披露需要保留为同一报告期的状态演进。把最终日期覆盖首次预约会失去延迟与预期变化信息。

映射约束：未来 adapter 必须区分来源原始值、标准化值和推导值；每条财务事实至少携带证券、报告期、公告/可得日期、报表类型、合并范围、单位/币种、来源和版本/provenance。缺失的版本信息不得由抓取时刻补造。

来源边界

公告链接不是结构化财务

审计报告若依赖公告 PDF/HTML 解析，会引入格式漂移、下载策略、解析质量与再分发问题。本批未授权或设计该条解析链路。

禁止推断：字段数接近、当前值有公告日期或一次调用成功，都不能证明 Tushare 与 AKShare 同单位、同报表类型、同版本、同计算口径或同历史可得性。AKShare 代码许可证也不替代新浪、东方财富、巨潮的来源条款。

B04 继续条件

  1. 版本矩阵：选银行、非银、制造、ST、北交所各 3 只证券，跨年报/半年报/季报比对三表的报告期、公告日、类型、币种、单位与字段映射。
  2. 修订观察：在下一个披露窗口连续重跑，保存 schema fingerprint 与值指纹；确认同报告期是否会更新、是否能识别首次公告与修订。
  3. 累计/单季验证：将候选“按报告期”和“按单季度”指标，与原始三表和 Tushare 对照，定义允许推导的字段及容差。
  4. 预告和快报生命周期：对同一证券报告期的多条预告/快报比对公告顺序、区间、修订和正式财报替代关系；没有版本键不得覆盖。
  5. 审计明确降级：除非发现正式结构化来源，不以公告标题/PDF 文本抽取替代 FinaAudit；该能力继续由 Tushare 主用。
  6. 架构保持：若后续批准实现，来源 SDK 和字段只可位于 infrastructure/providers/akshare/；任务、应用、质量、持久化层仍只依赖 provider-neutral port。

下一优先验证

先做三表的点时版本与累计/单季矩阵，再做预约披露状态演进；这是决定财务数据能否用于回测的前提。

明确不做

不建财务表、迁移、API、定时任务、真实 adapter、公告/PDF 解析链路或 fallback 路由；不提交临时 volume、stub 或探针。
